# v3 설계 변경안

상태: v3에 적용한 설계와 검증 기준이다. 구현·오프라인 검증은 완료했고 실제 모델 검증은 별도다. [현재 상태](current-state.md), [검증 기록](v3-validation.md), [리팩터링 계획 A~G](refactoring-plan-v3.md)를 함께 확인한다.

## 공통 실행기

- 공통 과제 지침과 각 방식의 문법 안내를 분리한다. 다른 단계용 행동·설명이 섞이지 않게 한다.
- 응답 스키마도 현재 단계와 준비/작업 상태에 맞춘다. 작업은 `send`, `revise`, `wait`, `submit`, 명시적 `stop`을 지원한다. 사전 제안·수락은 6단계 준비 중에만 제공한다.
- 형식 오류는 같은 규칙으로 교정할 수 있게 하되, 정답·실제 원자료의 교정값은 알려 주지 않는다.
- 제안·수락 대화를 의무화하지 않는다. 동일한 유효 일정 제출을 성공으로 판단하고 실제 대화 절차는 관찰한다.
- `send`는 제출 보존, 성공적으로 전달된 `revise`는 양쪽 제출 무효화라는 규칙을 적용한다.

## 자원 사용과 종료

- 토큰·시간·메시지·행동·합의 횟수를 연구용 종료 상한으로 사용하지 않는다. 남은 예산에 맞춰 행동하라는 지시도 주지 않는다.
- `max_turns`, `max_messages`, `max_language_turns`, `max_trial_tokens`, `trial_timeout_seconds` 등의 중단 경로를 제거한다. 설정 숫자만 키우는 방식은 사용하지 않는다.
- `turn_timeout_seconds`와 상위 RPC·이벤트 대기 제한이 느린 모델 응답을 자동 중단하지 않도록 대기와 취소를 분리한다. 폴링은 상태 확인이며 과제 제한이 아니다.
- 일괄 본문 바이트 예산도 제거한다. 문법·자료형·유한한 문제의 의미 범위는 공통 명세로 유지한다. 실제 장치·서비스의 기술 한계는 기록한다.
- 반복·`wait` 횟수로 자동 실패 처리하지 않는다. 반복 상태를 표시하고 Agent의 명시적 중단·사용자 취소·실제 서비스 오류를 구분한다.
- 사용량이 많다는 이유로 생성된 응답을 버리지 않는다. 사전 합의·교정까지 실제 사용량과 시간에 포함한다.
- Agent의 `stop`이나 최종 제출 실패는 해당 회차를 끝내고 계획된 다음 회차로 진행할 수 있다. 사용자 취소는 묶음을 중단하며, 인프라 오류는 새 회차 배정을 멈춘다.

## 공통 소통 기능

사실, 팀 요약, 특정 사실·요약 질문, 후보 일정·점수 평가, 이전 메시지 재확인, 제안·수정·수락·반려를 공통 의미 명세로 정의한다. 각 방식은 이에 대응하는 문법을 갖는다.

자연어는 원문으로 전달하고 중간 모델로 JSON으로 번역하지 않는다. 구조화 메시지의 공통 의미는 그대로 복원돼야 한다. 4단계의 벡터 용량과 5단계의 명령, 6단계의 기호 사전에도 같은 기능을 반영한다. 큰 메시지 참조 ID를 잘라내거나 정밀도를 잃지 않게 한다.

예제는 별도 설명용 입력을 사용하고 같은 정보와 행동을 보여 준다. 설명 글자 수나 전략을 똑같이 강제하지 않는다. 자연어의 추가 자유 표현과 구조화 방식의 범위 차이는 공개한다.

## 기록·평가

- 호출·원문 응답·파싱·행동·전달·제출·거절·중단을 ID로 연결한다. 전달된 것과 생성만 된 것을 구분한다.
- 같은 의미의 참·거짓·생략·모호함을 같은 기준으로 판정한다. 미제출은 해당 없음, 미검수는 미측정으로 기록한다.
- 주장 종류·반복과 고유 주장 수·판정 범위를 함께 보고, 오류 수만으로 순위를 만들지 않는다.
- 자연어 전체 검수와 표본 재검수 절차를 제공한다. 검수는 실행 후에 하며 Agent에게 평가 결과를 보내지 않는다.
- 사후 검수 결과는 원본 해시·평가 코드·의미 명세·검수 입력·검수자·시각과 함께 새 버전으로 저장한다. 내보내기 과정에서 재채점하지 않는다.

## 문제·배정·보고

이전 문제는 테스트 fixture로 옮겼다. 확인용 문제 하나를 실제 모델 결과를 보기 전에 구조 기준으로 선정·고정하고 독립 검산했다. 삭제된 과거 실행이나 그 수치를 검증 자료로 다시 요구하지 않는다.

방식별 5회와 대응되는 선발화·정보·문제 조건을 고정한다. 단독 요청은 해당 방식만, 다중 요청은 요청한 방식만 실행한다. worktree와 실제 실행 부하 조건을 구분하고 동시 실행 수·순서·대기 시간을 기록한다.

다섯 지표의 정의는 [실험 명세](phase-1-experiment.md)를 따른다. API 단가 추정과 총비용, 로컬 패킷과 전체 네트워크 트래픽을 혼동하지 않는다. 실제 실행 완료와 사후 내용 검수 완료는 별도 상태다.

## 구현 완료를 확인할 증거

| 대상 | 필요한 검증 |
|---|---|
| 실행기 | 자원 사용량이 커져도 정상 행동 적용, 제출·수정·중단 상태의 일관성 |
| 대기·취소 | 느린 응답·지연 알림·EOF·사용자 취소 구분, 중복 호출 없음 |
| 코덱 | 공통 의미·조합·경계·큰 참조의 정확한 복원과 동일한 오류 규칙 |
| 평가 | 같은 의미의 판정, 미제출·부분 검수·반복·모순·잘못된 요약 처리 |
| 배정 | 요청된 단계와 다섯 슬롯만 실행, 중단한 시도 대체 금지, 조건 기록 |
| 보고 | 원본과 수치의 대조, 검수 버전 선택, 처리 상태가 보이는 대화 기록 |

이 검증은 특정 방식의 승리를 요구하지 않는다. 공정성을 절대 보장하는 선언 대신 통제한 조건·남은 차이·검증 범위를 명시한다.
