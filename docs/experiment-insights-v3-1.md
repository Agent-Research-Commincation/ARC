# 여섯 소통 방식 실험 보고서

두 AI Agent가 서로 다른 정보를 가지고 하나의 일정을 정할 때, 소통 방식에 따라 대화와 결과가 어떻게 달라질까? 이 프로젝트는 그 과정을 실제 대화 기록으로 살펴본다.

2026년 9월 11일, 같은 일정 문제를 여섯 방식으로 각각 5회씩 실행했다. 이 보고서는 **방식별 효율성 가설 → 공통 회의 문제와 단계별 과정 → 실험 결과 → 핵심 인사이트** 순서로 이번 30회를 설명한다. 여기서 ‘단계’는 소통 방식의 번호다. 1단계부터 6단계까지 순서대로 학습하거나 발전시키는 실험은 아니다.

## 1. 프로젝트 가설: 어떤 소통 방식이 효율적인가

프로젝트의 중심 질문은 **두 Agent가 같은 문제를 해결할 때, 어떤 방식으로 소통하는 것이 효율적인가**다. 이를 여섯 방식 각각에 대한 질문으로 나누었다.

| 단계 | 확인하려는 가설 | 기대하는 효율 |
|---|---|---|
| 1 · 자연어 | **자연어로 소통하는 게 효율적인가?** | 필요한 정보를 문장으로 간결하게 설명하면 적은 대화와 모델 비용으로 정확한 합의에 도달할 수 있다. |
| 2 · JSON | **정해진 JSON 항목으로 소통하는 게 효율적인가?** | 사실·질문·후보를 구분해 전달하면 정보를 확인하기 쉬워져, 추가 설명이나 잘못된 결정을 줄일 수 있다. |
| 3 · 논리식·관계 표현 | **사실과 관계를 논리식으로 표현하는 게 효율적인가?** | 관계를 명확하게 적으면 해석의 모호함을 줄이면서 간결하고 정확하게 협업할 수 있다. |
| 4 · 고정 의미 특성 벡터 | **정보를 고정된 숫자 배열로 바꿔 전달하는 게 효율적인가?** | 정보를 정해진 좌표로 변환·복원하는 방식이 텍스트 교환보다 전송과 처리에 유리할 수 있다. |
| 5 · 바이트코드 | **짧은 명령을 바이너리로 바꿔 소통하는 게 효율적인가?** | 같은 의미를 적은 바이트로 전달해, 결과 품질을 유지하면서 전송 부담을 줄일 수 있다. |
| 6 · 공동 기호 언어 | **Agent끼리 기호를 합의한 뒤 소통하는 게 효율적인가?** | 공통 기호를 정하고 사용하면 이후 대화가 간결하고 명확해져, 합의에 든 비용을 상쇄할 수 있다. |

표의 기대는 확인하려는 가설이며 실험 결과를 뜻하지 않는다. 효율은 **결과 품질을 유지하면서 모델 비용·완료 시간·전송량·통신 처리가 얼마나 필요한가**로 평가한다. 예를 들어 빨리 끝났어도 잘못된 일정이라면, 시간만으로 효율적이라고 판단하기 어렵다.

이번에는 같은 일정 문제에서 각 구현의 실제 행동을 관찰했다. 위 질문은 연구 목적을 설명하기 위해 정리한 것이며 사전 등록한 통계 검정 가설은 아니다. 방식별 지침·문법·정보 공유·전송 처리가 함께 달라질 수 있으므로, 관측 차이를 표현 방식 하나의 효과로 확정하지 않는다.

## 2. 공통 문제와 각 단계별 과정

### 공통으로 해결하려던 문제: 두 팀의 회의 일정 정하기

두 회의 담당자가 각자 자기 팀의 일정만 알고 있다고 생각해 보자. 한쪽이 가능한 시간을 알려 주면 다른 쪽은 자기 팀의 정보와 맞춰 보고, 후보를 제안하거나 추가로 질문해야 한다. 두 담당자는 대화를 통해 모두 참석할 수 있는 시간을 찾고, 그중 참석자들이 더 선호하는 일정을 선택해야 한다.

이 실험에서는 두 담당자를 Agent A와 B로 두었다. 여섯 단계 모두 이 문제를 해결하며, 정보를 주고받는 방식이 달라진다.

참석자 6명의 회의 3개를 12개 시간대에 배치한다. 기록에서 시간대는 ‘슬롯’이라고 부르며 번호는 0부터 11까지다. Agent A는 A1·A2·A3의 참석 가능 시간과 선호 점수를, Agent B는 B1·B2·B3의 정보만 받는다.

| 회의 | 참석자 |
|---|---|
| M1 | A1, A2, B1 |
| M2 | A2, B1, B2 |
| M3 | A1, A3, B2, B3 |

모든 참석자가 가능한 시간이어야 하고, 공통 참석자가 있는 회의는 겹칠 수 없다. M1은 M3보다 먼저 열려야 한다. 이 조건을 지키면서 회의별 참석자 선호 점수의 총합을 최대화한다. 같은 사람이 여러 회의에 참석하면 각 회의의 선호를 모두 더한다.

대화에서 ‘팀 요약’은 특정 회의·시간에 자기 팀 참석자가 모두 가능한지와 그 사람들의 선호 점수 합계를 뜻한다. 예를 들어 M1의 A팀 요약에는 A1·A2만, B팀 요약에는 B1만 들어간다. 두 팀의 정보를 함께 봐야 회의 전체의 가능 여부와 점수를 알 수 있다.

사후 검산에서 유효한 일정은 54개였다. 유일한 최적 일정은 **M1을 슬롯 1, M2를 슬롯 6, M3를 슬롯 10에 배치하는 20점 일정**이다. 정답과 사후 평가 내용은 실험 중 Agent에게 제공하지 않았다.

### 같은 조건에서 무엇을 자유롭게 정하게 했는가

| 항목 | 실제 적용한 조건 |
|---|---|
| 모델 | 두 Agent 모두 `gpt-5.6-luna`, 추론 수준 `high` |
| 문제와 반복 | 같은 문제를 방식별 5회, 총 30회 실행 |
| 세션 | 매회 새 A·B 세션 사용, 총 60개 세션 |
| 먼저 말하는 역할 | 각 방식에서 회차 순서대로 A·B·A·B·A |
| 실행 환경 | 같은 코드 버전의 단계별 worktree에서 여섯 방식을 병렬 실행; 각 방식의 5회는 순차 실행 |
| Agent의 선택 | 원자료·요약 중 무엇을 보낼지, 무엇을 질문하고 언제 제안·수정할지 자율 선택 |
| 자원 사용 | 연구용 토큰·시간·메시지·행동·사전 합의 횟수 예산 없음 |

worktree는 코드와 결과가 섞이지 않도록 나눈 작업 폴더다. 이전 회차의 대화는 새 세션으로 넘어가지 않는다. 다만 같은 머신·계정·서비스를 사용하므로 서버 캐시와 서비스 부하까지 분리한 것은 아니다.

한 회차는 다음 순서로 진행된다.

1. A와 B가 공통 규칙과 자기 팀의 비공개 정보를 받는다.
2. Agent가 자료 전달, 질문, 후보 제안 등의 행동을 선택한다. 6단계는 먼저 기호 사전을 합의한다.
3. 실험 진행 프로그램인 실행기가 지정된 형식으로 메시지를 전달한다. 형식 오류로 거절되면 상대에게 전달되지 않으며, 거절된 요청의 시간과 모델 사용량도 기록한다.
4. 양쪽이 일정을 최종 제출하면 일치 여부와 유효성을 판정한다. 일반 메시지 `send`는 기존 제출을 유지하고, 전달에 성공한 수정 메시지 `revise`는 양쪽 제출을 무효화해 다시 제출하도록 알린다.
5. 종료 후 최적성과 대화 내용의 정확성을 따로 평가한다. 실패한 회차도 결과에 포함한다.

### 메시지는 어떤 모습으로 오갔는가

아래 표는 소통 본문이 바뀌는 경로다. 메시지를 전송 형식으로 바꾸고 복원하는 프로그램을 ‘코덱’이라고 부른다. ‘바이트’는 전송 데이터 크기이고, ‘토큰’은 모델 사용량의 단위다. 작은 바이트 수가 곧 작은 토큰 수를 뜻하지는 않는다.

| 단계 | 보내는 Agent가 작성 | 실험 채널에서 전송 | 받는 Agent가 읽음 |
|---|---|---|---|
| 1 · 자연어 | 영어 문장 | 작성한 문장 그대로 | 같은 문장 |
| 2 · JSON | 항목이 정해진 JSON | 작성한 JSON 그대로 | 같은 JSON |
| 3 · 논리식·관계 표현 | 정해진 관계식 | 작성한 관계식 그대로 | 같은 관계식 |
| 4 · 고정 의미 특성 벡터 | JSON | 의미별 고정 좌표에 값을 담은 숫자 배열 | 배열에서 복원한 JSON |
| 5 · 바이트코드 | 정해진 짧은 명령 | 명령을 변환한 바이너리 | 바이너리에서 복원한 JSON |
| 6 · 공동 기호 언어 | 합의한 기호로 쓴 관계식 | 작성한 관계식 그대로 | 같은 관계식 |

4단계는 학습 임베딩이나 모델 내부 상태를 교환하는 방식이 아니다. 6단계는 정해진 문법 안에서 기호 이름을 합의하며, 새 문법 자체를 만드는 실험은 아니다.

아래 사례는 **실제 기록을 한국어로 요약한 대화 흐름**이다. 원문 발화를 그대로 번역한 인용문은 아니다. 결과의 차이를 설명하기 위해 사후에 고른 사례이며, 그 흐름이 다섯 회 모두에서 반복됐다는 의미도 아니다. 전체 30회는 결과 집계에 포함했다.

### 1단계 · 자연어: 팀 요약을 읽고 후보를 수락한다

Agent는 가능한 시간과 선호를 문장이나 목록으로 설명한다. 상대는 이 문장을 읽고 자기 팀의 조건과 맞춰 본다.

**3회차의 흐름**

1. A가 자기 팀의 회의별 가능 시간과 선호 합계를 보냈다. 이 요약은 원자료와 일치했다.
2. B가 M1=4, M2=6, M3=10을 제안하면서 최적이며 총점이 24점이라고 설명했다.
3. A가 같은 후보를 수락했고, B와 A가 차례로 동일한 일정을 제출했다.

이 일정은 모두 참석할 수 있었지만 실제 점수는 18점이었다. B가 M1의 합계를 실제 2점 대신 8점으로 적어 총점도 6점 높게 설명했다. 대화는 합의에 도달했지만 최적 20점에는 미치지 못했다. A가 수락한 이유가 B의 잘못된 총점을 믿었기 때문인지는 기록만으로 알 수 없다.

### 2단계 · JSON: 정해진 항목으로 요약과 질문을 교환한다

Agent는 사실, 팀 요약, 질문, 후보 일정을 정해진 JSON 항목에 넣는다. 실행기는 형식을 확인하지만, 그 값이 실제 입력에 맞는지 대신 풀어 주지는 않는다.

**2회차의 흐름**

1. B가 자기 팀의 요약 72개와 A팀에 대한 질문 6개를 보냈다.
2. A가 M1=1, M2=6, M3=10 후보와 일부 팀 요약을 보냈다.
3. B가 아직 받지 않은 A팀 요약 26개를 추가로 질문했고 A가 답했다.
4. 양쪽이 처음 제안된 후보를 그대로 최종 제출했다.

결과는 최적 20점이었다. 다만 추가 질문 전부터 이미 최적 후보가 나와 있었고, 대화에 포함된 요약에는 오류 2건이 남았다. 잘못된 값은 최종 일정에 사용하지 않은 회의·슬롯 조합의 선호 합계였다. 형식에 맞는 JSON과 정확한 내용은 별도로 확인해야 한다.

### 3단계 · 논리식·관계 표현: 관계를 명확히 적어도 결정은 Agent가 한다

Agent는 `at(M2,5).`처럼 정해진 관계식으로 메시지를 쓴다. 이 표현은 M2를 슬롯 5에 배치한다는 뜻이다. 문법이 논리식처럼 보이더라도 자동 증명기가 최종 결정을 보장하는 구조는 아니다.

**4회차의 흐름**

1. B가 자기 팀의 요약 72개를 보냈다. 요약은 모두 정확했고 전송 과정에서도 의미가 보존됐다.
2. A가 M1=1, M2=5, M3=10을 제안했다.
3. B가 수락한 뒤 양쪽이 같은 일정을 제출했다. 그 사이 추가 질문이나 후보 수정은 없었다.

A가 가진 원자료에서 A2는 슬롯 5에 참석할 수 없었다. 따라서 M2를 그 시간에 배치한 일정은 무효였고 회차는 실패했다. 이 사례에서 놓친 것은 A 자신의 제약이다. 상대가 보낸 정확한 정보만으로 전체 결정의 유효성이 보장되지는 않았다.

### 4단계 · 고정 의미 특성 벡터: 숫자 배열로 보내고 JSON으로 읽는다

Agent는 JSON을 작성한다. 변환기가 각 의미를 미리 정한 숫자 좌표에 넣어 전송하고, 상대에게는 다시 JSON으로 복원해 준다. 모델이 숫자 배열을 직접 해석하는 실험은 아니다.

**5회차의 흐름**

1. A가 자기 팀 요약을 보내며 B팀 자료를 요청했다.
2. B가 M1=8, M2=6, M3=10을 제안했다. 같은 메시지에는 B팀이 M1의 슬롯 8에 참석할 수 없다는 요약도 있었다.
3. A가 `revise`로 M1을 슬롯 1로 바꾸고, 새 후보가 유효하며 20점이라고 명시했다.
4. B가 수락했고 양쪽이 수정한 최적 일정을 제출했다.

### 1. 가장 빠른 방식과 가장 작게 보내는 방식은 달랐다

자연어는 낮은 모델 비용과 짧은 평균 시간, 바이트코드는 작은 전송량에서 강점을 보였다. 따라서 이번 결과를 활용할 때는 어떤 비용을 줄이려는지 먼저 구분해야 한다.

자연어는 작업 메시지 15개와 실행기 요청 25턴으로 다섯 회를 마쳤고, 평균 입력·출력 토큰도 가장 적었다. 간결한 정보 교환과 적은 요청이 낮은 비용에 기여했을 가능성이 있다. 다만 지침 길이와 캐시도 함께 달라졌으므로, 자연어 표현만의 효과나 다른 과제에서의 우열까지 입증한 것은 아니다.

### 2. 서로 동의했다는 사실만으로 좋은 결과가 되지는 않았다

자연어 3회차는 잘못된 점수 설명 뒤 같은 일정에 합의했지만 실제 점수는 최적보다 낮았다. 논리식 4회차는 상대의 요약이 정확했어도 자기 팀의 참석 불가 조건을 놓쳐 실패했다. JSON은 최적해로 끝난 회차에도 내용 오류가 남아 있었다.

이 사례들은 **형식의 정확성, 전달 내용의 정확성, 최종 일정의 품질을 따로 확인해야 한다**는 점을 보여 준다. 수락이나 최적 제출 하나만 보고 대화 전체가 정확했다고 판단할 수 없다. Agent가 내부에서 어떤 계산을 생략하거나 어떤 수치를 믿었는지는 실제 발화와 제출에서 확인되는 범위까지만 설명할 수 있다.

### 3. 전송 크기를 줄여도 모델이 처리하는 양은 따로 늘어날 수 있다

벡터는 모든 작업 본문이 32,773바이트인 고정 구조였다. 짧은 수락도 같은 크기였고 평균 채널 크기는 JSON의 약 24.01배였다. 이 차이는 이번 저장 구조로 설명할 수 있으며, 학습 임베딩이나 벡터 표현 일반의 비효율을 뜻하지 않는다.

반대로 바이트코드는 채널 평균이 JSON보다 78.46% 작았지만 평균 입력 토큰은 더 많았다. 모델은 복원된 JSON과 누적 대화를 읽었으며, 질문 범위와 대화량도 방식마다 달랐다. 같은 메시지를 코덱만 바꿔 보낸 비교가 아니므로, 이 전송 절약률을 모델 비용 절약률로 바꿀 수 없다.

관측 모델 비용은 바이트코드가 JSON보다 4.61% 낮았으나, 같은 기록 토큰에서 캐시 할인만 없애는 가상 계산에서는 성공당 JSON $0.015309, 바이트코드 $0.015834로 순서가 바뀌었다. 이는 실제 캐시 없는 실험이 아니라 비용 해석의 민감도를 보여 주는 계산이다.

### 4. 공동 언어의 부담은 사전을 정한 뒤에도 발생했다

사전 합의는 모든 회차에서 제안·수락 2개 메시지로 끝났고 평균 11.16초였다. 긴 지연을 합의 시간만으로 설명할 수는 없다. 4회차는 합의 이후 문법을 반복해서 고쳤고, 이 회차 하나가 공동 언어 방식 모델 비용의 49.00%를 차지했다.

그 회차의 거절 요청 31개에 포함된 모델 비용은 약 $0.031554, 입력부터 응답까지의 경과 시간 합계는 264.26초였다. 합의한 이름, 예제, 문법 규칙, 오류 안내의 조합이 회복을 어렵게 했을 가능성이 있다. 이 요청에는 문제 풀이와 문맥 처리도 포함되므로 통신만의 비용이나 개선 후 그대로 절약할 금액으로 볼 수는 없다.

### 5. 대화를 더 했다는 사실보다 무엇을 고쳤는지가 중요했다

벡터 5회차에서는 잘못된 후보를 수정해 최적해에 도달했다. JSON 2회차는 추가 질문 전부터 최적 후보가 있었고, 이후 교환에도 내용 오류가 남았다. 공동 언어 3회차에서는 A가 요약을 다시 보내며 오류 8건을 바로잡았지만 맞던 항목 4개를 새로 틀리게 바꿨다. [해당 관찰 기록](../results/readable/20260911T092336Z-plan-cfd3ab2b1222-review-v3-1/stage-06-shared-dictionary/trial-03/observation.md)에서 변경을 확인할 수 있다.

따라서 교정의 효과를 읽으려면 어떤 정보를 확인했고, 값과 후보가 실제로 어떻게 바뀌었는지를 따라가야 한다. 이번 자료는 추가 대화의 회복 사례와 새 오류 사례를 모두 제공하지만, 대화를 늘리면 항상 좋아진다는 결론은 제공하지 않는다.

이번 실험의 인사이트는 한 문제·한 모델·방식별 5회의 관찰에 근거한다. 새 세션 60개 중 20개는 첫 호출부터 캐시가 관측됐고, 사람의 독립적인 내용 검수와 독자 이해도 평가는 아직 수행하지 않았다. 방식별 보편적인 추천, 표현 하나의 인과 효과, 단일 Agent 대비 이득은 [후속 연구](phase-1-experiment.md)의 질문으로 남는다.
