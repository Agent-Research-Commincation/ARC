# 1~6단계 요청 기반 실험 운영

상태: v1 실행기와 여섯 모듈 구현 완료. 기본 상태 협업을 동일 조건에서 매회 새 세션으로 5회 실행해 전부 26점 최적해로 성공했다. 오프라인 테스트 55개 통과. 여섯 방식별 전송 검증과 단계별 본실험은 아직 미수행이다.

## 1. 사용자 요청

단계는 소통 방식 번호이다. 연구의 1차·2차·3차 확장 단계나 소프트웨어 구현 순서를 의미하지 않는다. 어느 단계든 독립적으로 요청할 수 있다.

| 요청 | 실행 명령 | 소통 방식 |
|---|---|---|
| 1단계 해줘 | `python3 lab.py run 1` | 자연어 |
| 2단계 해줘 | `python3 lab.py run 2` | JSON |
| 3단계 해줘 | `python3 lab.py run 3` | 논리식·관계 그래프 |
| 4단계 해줘 | `python3 lab.py run 4` | 의미 벡터 |
| 5단계 해줘 | `python3 lab.py run 5` | 바이트코드 |
| 6단계 해줘 | `python3 lab.py run 6` | Agent 공동 언어 |

각 명령은 해당 단계만 5회 순차 실행한다. 같은 단계의 재실행은 새 실행 ID를 사용한다. 자연어 요청의 명령 연결은 [AGENTS.md](../AGENTS.md)에 기록했다.

## 2. 공통 구조

| 파일 | 역할 |
|---|---|
| `lab.py`, `experiment/cli.py` | 단계별 명령, 상태·검증·비교 |
| `config/experiment.json` | 모델, 반복 횟수, 상한, 추정 단가 |
| `config/problem.json`, `experiment/problem.py` | 고정 일정, Agent별 입력, 평가기와 최적해 계산 |
| `experiment/codex.py` | App Server 초기화, 독립 세션·턴 진행, 사용량 수집 |
| `experiment/protocols.py` | 여섯 메시지 표현·검증·변환 모듈 |
| `experiment/runner.py` | 언어 합의·메시지 전달·종료·계측·저장 |
| `tests/test_experiment.py` | 모델 호출 없는 검증 |

Python 표준 라이브러리를 사용한다. Codex 설치 버전에서 JSON Schema를 생성해 App Server 요청 형식과 격리 설정을 확인했다. 구현은 턴의 구조화된 최종 응답을 받는 방식이며 맞춤 동적 도구를 추가하지 않는다. [공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)

## 3. 세션과 정보 접근

- 매회 새 App Server 프로세스와 새 A·B 세션을 사용한다. Luna high를 명시하고 실제 반환된 모델·추론 수준을 검사한다.
- A는 A1~A3의 일정과 선호만, B는 B1~B3의 일정과 선호만 받는다. 회의 구성과 슬롯 목록은 공통이다.
- 공통 입력의 `slot_indexing`에 0~11 슬롯 ID와 시간 대응표를 넣는다. 가능 시간·선호 배열과 메시지·최종 제출은 같은 ID를 사용한다.
- 실험 Agent는 기획 대화, 상대 캘린더, 정답, 기존 결과를 상속하지 않는다.
- 비어 있는 임시 작업 디렉터리와 환경 목록을 사용한다. 셸·앱·플러그인·MCP·추가 Agent·메모리·웹 검색과 지침 파일 탐색을 비활성화한다.
- 실제 반환된 지침 파일 목록이 비어 있지 않거나 모델이 변경되면 정상 실행으로 처리하지 않는다. 예상하지 않은 도구 호출도 중단 사유다.
- 평가기는 별도 Python 코드이다. 모델에 최적 점수나 전역 조건 검사 도구를 제공하지 않는다.

실행기는 A부터 번갈아 대화 기회를 준다. 각 기회에서 무엇을 보내고 질문·제안·수정할지, 기다리거나 제출할지는 Agent가 정한다. 형식 오류 메시지는 상대에게 전달하지 않고 송신 Agent가 수정할 기회를 갖는다.

## 4. 여섯 표현 방식의 구현 정의

모든 방식은 공통 제어 외피에서 행동을 선택한다. 외피가 JSON이라고 해서 모든 실험을 JSON 방식으로 분류하지 않는다. 상대에게 전달하는 본문의 표현과 수신 처리가 비교 대상이다.

### 1단계: 자연어

영어 문장으로 자유롭게 메시지를 작성한다. JSON 객체·배열이나 코드 블록으로 시작하는 메시지는 거절한다. 의미 내용 전체를 기계적으로 검증하지는 않으며 세부 준수 여부는 원본 기록으로 검토한다.

### 2단계: JSON

`kind`, `facts`, `schedule`, `requests`를 사용한다. 메시지 종류는 정보·질문·제안·수락·거절이다. 참석 가능 여부와 선호 점수의 임의 부분집합을 전달할 수 있다. 자유 텍스트 필드, 중복 키·사실, 범위 밖 값은 거절한다.

### 3단계: 논리식·관계 그래프

`inform().`, `available(A1,0,1).`, `preference(A1,0,2).`, `at(M1,1).`, `ask(B1).`처럼 관계를 전달한다. 수신 모델은 검증된 논리식 원문을 받는다. v1은 제한된 관계 문법이며 범용 논리 증명기를 포함하지 않는다.

### 4단계: 의미 벡터

송신 모델이 JSON으로 선택한 의미 프레임을 외부 코덱에 준다. 메시지 종류 5개, 참석 가능 여부 72개, 선호 72개, 회의 배치 3개, 질문 대상 6개의 총 158개 특성을 고정 벡터에 넣는다. 256차원으로 패딩한 뒤 정규화된 Hadamard 직교 변환을 적용해 256개 float32, 1,024바이트를 전송한다.

수신 측은 전송 바이트만 역변환하여 의미 프레임을 복원한다. 원래 JSON 본문을 우회 전달하지 않는다. 이 방식은 손실 없는 고정 의미 특성 코덱이다. 학습 임베딩·의미 검색·모델 내부 잠재 상태 통신을 구현한 것은 아니다. 수신 모델은 복원된 의미 프레임을 읽는다.

### 5단계: 바이트코드

송신 모델이 `KIND`, `AV`, `PREF`, `AT`, `ASK` 명령을 선택한다. 컴파일러가 바이너리 명령으로 변환하고 수신 VM은 그 바이트만 실행해 의미 프레임을 만든다. 명령은 메시지 사실·제안 데이터를 구성하는 기능만 갖는다. 호스트 코드 실행, 파일 접근, 상대 캘린더 조회, 자동 최적화 명령은 없다.

### 6단계: 공동 언어

개인 일정 제공 전에 두 Agent가 아홉 의미의 기호 이름을 제안하고 수락한다. B는 A의 제안을 수락하거나 대안을 제안할 수 있다. 상대 제안에 대한 명시적 수락이 있어야 작업을 시작한다.

고정 문법과 참석자·회의 ID는 유지하고 기호 사전만 정한다. 합의 후 이 기호로 논리식 메시지를 작성한다. 초기 합의는 JSON 제어 메시지를 사용하며 합의·수락 메시지의 통신량·모델 사용량·시간도 같은 회차에 포함한다. 매회 새 사전을 합의한다.

2~6단계는 v1에서 같은 유한한 일정 의미 범위를 표현한다. 표현 형식과 외부 처리 장치를 포함한 시스템 비교이며 결과를 다른 작업이나 임의의 언어 전체로 일반화하지 않는다.

## 5. 종료 규칙과 기본 상한

- 두 Agent가 각각 제출한 회의 배치가 같으면 평가기가 필수 조건을 검사한다. 배치가 다르면 합의 실패다.
- 제출 값은 상대에게 전달하지 않는다. 제안과 수락은 소통 모듈로 전달해야 한다.
- 제출 후 새 메시지가 나오면 기존 제출을 무효화한다.
- 두 Agent가 연속해서 기다리면 진행 불가로 종료한다.
- 회차당 600초, 모델 호출당 120초, 작업 대화 기회 24회, 메시지 20개, 본문 16,384바이트를 상한으로 둔다.
- 6단계 합의에는 최대 6회의 별도 기회를 사용하되 메시지·시간 상한은 작업과 공유한다.
- 누적 토큰 100,000을 호출 완료 후 검사한다. 호출 도중의 정확한 토큰 상한은 보장하지 않는다.
- 과제 실패는 기록하고 다음 회차로 진행한다. 계정·연결·모델 조건 같은 실행 인프라 오류는 묶음을 미완료로 남기고 중단한다.
- 성공 5회를 채우거나 오류를 감추는 자동 재실행은 하지 않는다. 사용자 재실행은 새 묶음으로 기록한다.

## 6. 다섯 지표와 기록

핵심 지표는 성공률·품질, 성공 1건당 총비용, 전체 완료 시간, 실제 통신량, 통신 처리 비용이다.

- 전체 완료 시간에는 App Server 초기화·세션 생성·언어 합의·모델 응답 대기·소통을 포함한다.
- 통신량은 로컬 채널에서 직렬화한 프레임의 4바이트 헤더 길이 + 공통 JSON 헤더 + 방식별 본문이다. Base64 로그 크기나 모델 API의 TLS/IP 트래픽을 뜻하지 않는다.
- 원본 모델 본문, 실제 전송 프레임, 수신 측 해석 결과를 각각 보존한다.
- 캐시 토큰과 추론 토큰을 중복 과금하지 않는다. 실제 구독 청구액은 알 수 없으므로 API 단가 기반 추정값과 구분한다.
- 로컬 CPU 단가는 기본 미설정이다. 총비용은 `null`로 두고 모델 비용만의 부분 추정을 별도 제공한다. CPU 단가를 설정하면 실행기·Codex 자식 프로세스의 CPU도 합산한 추정값을 계산한다.
- 통신 처리에는 로컬 코덱·검증·프레임 처리 시간을 기록한다. 모델 호출 내 작업 추론과 메시지 생성 비용은 분리 측정 불가다. 총비용에 통신 비용을 다시 합산하지 않는다.

`results/experiment/<실행 ID>/`에 `manifest.json`, `summary.json`, `report.md`와 각 `trial-NN/`의 `events.jsonl`, `result.json`을 저장한다. 6단계는 회차별 `language.json`도 남긴다. 결과를 외부 서비스에 게시하지 않는다.

공통 설정·문제·소스 코드·Codex 버전을 해시하여 비교 그룹을 구분한다. 설정이 바뀐 결과를 자동으로 합치지 않는다. 5회 미완료 묶음은 성공률과 성공 1건당 비용을 계산하지 않는다.

## 7. 준비 검증과 현재 상태

- `python3 lab.py check`: 모델 호출 없는 55개 테스트.
- `python3 lab.py observe`: 메시지 형식을 지정하지 않고 동일 과제를 매회 새 A/B 세션으로 5회 관찰. 공통 제어·입력·도구 제한은 유지하고, 회차별 원문은 `results/observation/`에 저장한다.
- `python3 lab.py verify-live`: 실제 Luna high로 여섯 단계의 메시지 전송·복원 점검. `--stage N`으로 한 단계만 검사 가능.
- `python3 lab.py pilot N`: 일정 과제 1회 예비 실행.
- `python3 lab.py status`: 로컬 구현과 실제 연결 검증 결과 구분.
- `python3 lab.py compare`: 기존 본실험을 같은 설정끼리 비교.

2026-09-09 기본 협업을 슬롯 번호표 보완 후 동일 조건에서 5회 실행했다. 세션 ID 10개가 모두 다르고 실제 반환 모델·추론 수준이 Luna high임을 확인했다. 다섯 회 모두 26점 최적해로 성공했고 회당 평균 완료 시간은 53.83초, 평균 통신량은 1,351.8 bytes다. 여섯 방식별 전송·복원 점검과 단계별 본실험은 남아 있다. [5회 상세 관찰과 원문](basic-observation-five-runs.md).

통상적인 Agent 소통을 대표하는 별도 기준 구성은 추가 연구 항목이다. 1단계 자연어를 자동으로 그 기준이라고 부르지 않는다.
