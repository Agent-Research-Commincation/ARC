# v3 리팩터링 실행 계획

상태: A~G 구현과 오프라인 검증 완료. 실제 모델 연결 검증·본실험은 미실시다. [현재 상태](current-state.md)와 [검증 근거](v3-validation.md)를 확인한다. 아래 작업 목록은 적용한 변경과 완료 기준을 남긴 것이며 소통 방식 번호 1~6과 관계없다.

## 목표와 완료 범위

같은 문제·초기 정보·모델·공통 행동 규칙에서 여섯 방식을 자율적으로 사용하고, 완료 과정과 실제 사용량을 관찰하는 실험실로 바꾼다. 구현 구조를 분리하는 작업과 행동·평가 명세를 바꾸는 작업을 구분해 검증한다.

- `gpt-5.6-luna` / `high`, 방식별 5회, 매회 독립 A·B 세션을 유지한다.
- 연구용 토큰·시간·대화·사전 합의 횟수 예산을 제거한다. 더 큰 상수나 숨은 대기 제한으로 대체하지 않는다.
- 문서 정리와 오프라인 구현 검증만으로 실제 모델 호출을 자동 추가하지 않는다. `check`와 `status`는 오프라인이다. 명시적으로 요청된 기본 협업 관찰이나 준비 범위의 연결 점검은 별도로 수행하며 본실험 요청을 대신하지 않는다.
- 한 단계 요청은 해당 단계만 5회, 여러 단계 요청은 요청한 단계만 수행한다. 실패를 성공으로 채우지 않는다.
- 여섯 방식의 문법과 Agent의 전략 선택을 유지하면서 과제에 필요한 공통 소통 기능과 평가 기준을 맞춘다.
- 삭제한 과거 실행 자료의 복원·이관은 범위에 포함하지 않는다. 아래 실행 원본·검수 결과 보존 규칙은 앞으로 생성하는 자료에 적용한다.
- 이번 리팩터링에 다른 모델, 학습 임베딩, 자유 문법 학습, 다중 문제 대규모 실행, 요소별 분리 실험을 자동 추가하지 않는다.
- Python 3.9 이상 표준 라이브러리와 기존 Codex CLI를 유지한다. 새 외부 패키지나 서비스는 요구하지 않는다.

## 모듈 책임

아래 책임 경계로 구현했다. 기존 의미 보존 테스트는 유지하고 달라진 정책의 기대값과 경계 검증을 추가했다.

| 모듈 | 최종 책임 |
|---|---|
| `contracts.py` — 추가 | 공통 행동·메시지 의미·상태·오류 타입, 단계·진행 상태별 응답 스키마 |
| `artifacts.py` — 추가 | 이벤트 기록, 원자적 파일 저장, 실행 스냅샷·해시와 원본 보존 |
| `codex.py` | 세션·RPC·이벤트 수신·사용량 전달·명시적 취소. 문제 채점과 단계별 전략을 알지 않음 |
| `trial.py` — 추가 | 한 회차의 상태 전이, 발언 기회, 합의·제출·수정·중단. 사용량으로 종료하지 않음 |
| `protocols.py` | 공통 의미를 각 표현·전송 형식으로 변환·복원. 원자료 조회나 정답 계산 없음 |
| `problem.py` | 입력 검증·공개/비공개 입력 분리·일정 평가·독립 검산 대상 |
| `evaluation.py` — 추가 | 사후 의미 평가와 오류 영향 계산. 모델 호출·파일 덮어쓰기 없음 |
| `metrics.py` — 추가 | 이벤트·결과에서 비용·시간·통신량·완료 상태를 집계하는 순수 함수 |
| `records.py` | 명시적인 사후 검수 실행, 검수 버전 관리, 사람이 읽는 기록 생성 |
| `scheduling.py` — 추가 | 요청된 단계와 5회 배정, 실행 순서, worktree 작업 조정과 취소 |
| `runner.py`, `cli.py` | 준비·실행·검수·비교 명령의 연결과 묶음 수명 관리 |

의존 방향은 공통 계약 → 코덱/백엔드/회차 실행 → 묶음 실행이다. 사후 평가·집계·표현은 기록을 읽는다. Agent에게 사후 평가 결과가 돌아가는 경로는 두지 않는다. 새로운 추상화 프레임워크나 범용 플러그인 시스템은 만들지 않는다.

## A. 소스 기준 기록과 공통 계약 확정

선행 조건: 없음.

작업:

1. 구현 시작 시 기존 수정 사항을 구분하고 현재 소스·설정·테스트의 기준 해시를 기록한다. 현재 작업 트리를 초기화하거나 기존 변경을 덮지 않는다. 삭제한 실행 결과는 기준 자료로 요구하지 않는다.
2. `contracts.py`와 `artifacts.py`의 최소 구조를 만든다. 공통 상태, 행동, 메시지 ID, 제출 버전, 오류 종류, 기록 버전을 정의한다.
3. 중단 행동은 `stop`으로 명시한다. 본문을 상대에게 전달하는 우회 채널로 쓰지 않으며, 작업과 6단계 준비 모두에서 동일하게 허용한다. 사유는 관찰자 기록에 남긴다.
4. `send`, `revise`, `wait`, `submit`, `stop`의 허용 상태와 효과를 표로 고정한다. 준비 중에는 사전 제안·상대 제안 수락·중단만 허용한다.
5. 현재 실행 설정을 v3 명세로 변경하면서 예산 키를 제거한다. v3 실행에 옛 예산 설정이 들어오면 조용히 무시하거나 큰 값으로 바꾸지 말고 명시적인 설정 오류로 알려 준다. 과거 결과를 읽기 위한 별도 설정은 만들지 않는다.
6. 공통 의미 명세에 사실, 요약, 특정 사실·요약 질문, 후보 평가, 메시지 재확인, 제안·수정·수락·반려를 정의한다. 같은 의미의 예문과 예상 판정을 테스트 자료로 고정한다.
7. 테스트용 문제·설정을 실제 실행 기본 설정에서 분리한다. 현재 문제는 개발용 자료로 명시하고, 본실험 확인용 문제는 F에서 별도로 선정·검산한다.

산출물: 공통 계약·이벤트 명세, v3 설정 명세, 소스 기준 해시, 공통 의미 예제 모음.

완료 기준:

- 단계·진행 상태별 스키마와 검증기가 같은 행동을 허용한다.
- 새로 생성한 테스트 기록의 원본 보존 검사와 잘못된 설정·필드 검사가 통과한다.
- 기존 행동을 단순 이동한 부분은 고정 테스트 입력에서 이동 전후 결과가 같고, 바뀌는 정책은 별도 테스트로 표시한다. 삭제한 실험 자료는 사용하지 않는다.

## B. 모델 응답 대기와 중단 처리 분리

선행 조건: A.

대상: `codex.py`, 백엔드 테스트.

작업:

1. `next_event(deadline)`를 취소 가능한 반복 이벤트 대기로 바꾼다. 짧은 폴링 주기는 상태 확인에만 쓰며, 큐가 잠깐 비어 있는 것은 모델 실패가 아니다.
2. `rpc`의 요청 ID·지연 응답·알림 보관을 유지한다. 응답이 늦다고 같은 모델 요청을 다시 보내지 않는다.
3. `turn`에서 고정 경과 시간에 따른 자동 중단과 `timeout or ...` 기본값 회귀를 제거한다. 초기화·시작 응답·턴 실행의 상위 대기도 함께 점검한다.
4. 사용자 취소 신호, 명시적 서버 오류, EOF·프로세스 종료, 모델 변경·금지 도구 호출을 각각 구분한다. 오래 걸린다는 사실만으로 프로세스가 죽었다고 판단하지 않는다.
5. 명시적인 취소 또는 실제 오류에서만 진행 중인 턴의 중단·정리 절차를 수행한다. 취소가 결정된 후의 프로세스 정리 대기는 유한하게 할 수 있으나 모델 작업 중단의 새 시간 예산으로 쓰지 않는다.
6. 턴 완료와 사용량 알림을 동일한 turn ID로 연결한다. 최종 사용량이 없으면 이전 누적값을 재사용하지 않고 미측정으로 기록한다. 보조 조회가 실패했다고 이미 받은 유효한 모델 응답을 폐기하지 않는다.
7. 현재 모델·추론 수준 확인, 도구·외부 지침 차단, 내부 추론 본문 비수집을 유지한다.

완료 기준:

- 가짜 시계로 기존 120초·600초를 넘겨도 살아 있는 요청은 진행 상태를 유지한다.
- 늦은 알림·다른 RPC 응답·EOF·취소가 각각 정확히 처리되고 모델 호출을 중복 생성하지 않는다.
- 중단 경로가 기록을 남기고 자식 프로세스를 정리한다. 느린 응답과 서비스 실패를 구분한다.

## C. 한 회차를 명시적인 상태 전이로 분리

선행 조건: A·B.

대상: 새 `trial.py`, `runner.py`의 기존 `Trial`, 이벤트·실행기 테스트.

작업:

1. `Trial`을 `trial.py`로 옮기고 시간·토큰을 검사하는 `remaining()`을 제거한다. 누적 카운터는 측정용으로만 남긴다.
2. 고정 횟수 `for` 루프를 종료 상태까지 진행하는 루프로 바꾼다. 6단계 준비·작업·교정 모두 같은 취소·기록 체계를 쓴다.
3. 두 번 연속 `wait` 종료를 제거한다. `wait`는 발언 기회를 넘기고 반복은 관찰자 상태에만 표시한다. 이를 자동 실패 횟수 제한으로 대체하지 않는다.
4. 공통 지침과 단계별 지침을 구성하고, 현재 상태에서 허용하는 응답 스키마를 매 호출에 전달한다. 강제적인 제안·수락 횟수는 두지 않는다.
5. `send`는 제출 보존, 성공적으로 전달된 `revise`는 양쪽 제출 무효화라는 규칙을 유지한다. 거절된 수정은 제출을 지우지 않는다.
6. `request_id` → `response_received` → 파싱된 행동 → 적용/거절/중단을 연결한다. 원문 파싱 실패도 원문과 사용량이 빠지지 않게 기록한다.
7. 제출이 일치·유효하면 성공, 불일치·무효이면 해당 과제 종료 사유를 기록한다. `stop`은 명시적 진행 중단이며 문제에 해가 없다는 판정이 아니다.
8. 외부 취소·인프라 오류·서비스 제한은 과제 제출 결과와 별도 원인으로 남긴다. 회차가 중단돼도 부분 사용량과 마지막 확정 상태를 보존한다.

완료 기준:

- 같은 제출·확인·수정·거절 시나리오가 전 방식에서 같은 상태를 만든다.
- 예전의 24행동·20메시지·100,000토큰·합의 6회를 넘기는 오프라인 시나리오가 이후 정상 제출까지 처리된다.
- 모든 생성 응답의 처리 상태가 추적되고, 대화 없는 유효한 공동 제출도 정의한 성공 기준대로 판정된다.
- Agent의 `stop`이나 최종 제출 실패는 현재 회차를 종료하며, 묶음은 예정된 다음 회차를 진행할 수 있다. 사용자 취소는 묶음을 중단하고, 인프라 오류는 새 회차 배정을 멈춘다. 이미 시작한 실패 회차를 다시 실행해 대체하지 않는다.
- 강제 프로세스 종료로 최종 기록을 남길 수 없었던 경우에는 마지막 확인 상태와 미확정 상태를 구분한다. 유실된 행동 결과를 추정해 성공·실패를 만들지 않는다.

## D. 공통 의미와 여섯 표현·전송 경로 정리

선행 조건: A·C.

대상: `contracts.py`, `protocols.py`, 문법 지침, 코덱·예문 테스트.

작업:

1. `empty_frame`, 공통 검증·정규화·의미 목록을 계약 계층으로 옮긴다. 코덱은 동일 의미를 입력받아 복원 결과를 반환한다.
2. 특정 개인 사실·팀 요약 질문, 후보의 유효성·점수 주장, 과거 메시지 재확인을 각 문법으로 표현한다. 재확인 참조는 이미 본 메시지 ID만 사용할 수 있게 공통 규칙을 둔다.
3. 자연어 원문은 그대로 전달한다. 구조화된 추가 필드 때문에 자연어를 중간 모델로 번역하거나 모든 전략을 같은 구조로 강제하지 않는다.
4. 고정 벡터·바이트코드·공동 기호 사전에 같은 의미 기능을 반영한다. 필요하면 벡터 차원·명령·사전 의미 목록을 바꾸고 버전을 올린다.
5. 전역 메시지 참조를 float32 하나에 넣어 정밀도를 잃거나 옛 메시지 횟수 범위로 자르지 않는다. 참조의 정확한 인코딩을 명세에 포함하고 큰 ID의 왕복을 검증한다.
6. 고정 16,384 B 제한을 제거한다. 논리식·어셈블리의 줄 수 제한도 살펴 공통 의미상 유효한 내용을 임의로 끊지 않도록 수정한다. 유한한 사실 영역·자료형·중복 규칙은 유지한다.
7. 공통으로 지원하는 의미의 최대 조합을 모두 실을 수 있는지 확인한다. 특정 방식만 일부 필드를 생략하거나 낮은 용량을 갖게 하지 않는다. 기술적 용량은 명세·측정표에 드러낸다.
8. 모델이 작성하는 표현, 실제 전송 본문, 상대가 읽는 표현을 별도로 문서화한다. 4는 학습 임베딩, 6은 새로운 문법 학습으로 소개하지 않는다.

완료 기준:

- 사실·요약·질문·평가·재확인·수정의 의미별 왕복, 조합·경계·잘못된 값·큰 참조 ID 검사가 통과한다.
- 원본 의미, 송신 본문, 복원 의미, 수신 텍스트의 연결을 각 방식에서 검증한다.
- 거짓이지만 문법상 유효한 주장도 전송된다. 실제 정답 여부를 실행 중 코덱이 교정하거나 알려주지 않는다.
- 자연어 대응 예문은 공통 의미를 표현하는지 검수하고, 자유 표현 전체가 동등하다고 주장하지 않는다.

## E. 사후 평가·비용 집계·검수 버전 분리

선행 조건: A·C·D.

대상: 새 `evaluation.py`, `metrics.py`, `records.py`, `runner.py`의 집계 함수.

작업:

1. `check_claim`, 의미 영향 계산과 `analyze_trial`의 순수 평가 부분을 실행기에서 분리한다. 상태·이벤트를 입력받고 평가 결과를 반환하게 한다.
2. 미제출 영향은 `null`과 해당 없음으로 기록한다. 생략·모호함·잘못된 주장·틀린 요약·수정된 주장을 구분한다.
3. 주장 종류별 맞음/틀림/판정 불가와 분모를 기록한다. 반복 횟수와 고유 주장 수를 함께 제공하고, 반복과 상충되는 주장 버전을 정규화 과정에서 지우지 않는다.
4. 생성·교정 오류, 전달된 내용, 코덱 보존, 최종 결과의 측정 범위를 나눈다. 판정할 수 없는 거절 문자열에 의미를 임의로 부여하지 않는다.
5. 자연어 전체 검수 양식과 표본 재검수 절차를 제공한다. 원문 근거·검수자·미완료 항목을 저장한다. 구조화 표현도 같은 의미 기준의 사례를 통과해야 한다.
6. `model_cost`, `summarize` 등을 `metrics.py`로 옮긴다. 캐시·추론 토큰 중복 합산 방지, 실패·합의·교정 비용 포함, 미측정은 null이라는 규칙을 유지한다.
7. 계획·시작·종료·과제 제출 완료·운영상 중단·검수 완료를 별도 상태와 개수로 집계한다. 미실행 회차를 실패나 성공으로 만들지 않고, 중단 회차를 분모에서 조용히 제외하지 않는다.
8. 계획된 다섯 시도의 상태가 모두 확인된 경우의 관측 성공 비율과 미실행·미확정 항목이 있는 묶음의 현재 완료 수를 구분한다. 인프라 중단을 포함한 관측 비율을 모델의 문제 해결 능력 추정치로 해석하지 않는다. 성공당 비용은 필요한 전체 사용량이 확인될 때 계산하며, 부분 합계와 전체 추정을 구별한다.
9. 사후 평가는 `results/reviews/<run-id>/<review-id>/`에 새로 저장한다. 원본 해시·평가 코드 해시·의미/코덱 버전·검수 입력·검수자·시각을 포함한다. 기존 실행 원본에 새 평가를 덮어쓰지 않는다.

완료 기준:

- 같은 의미의 참·거짓·생략·모호함 사례가 형식에 따라 다른 판정을 받지 않는다.
- 미제출, 부분 검수, 반복, 모순, 틀린 요약, 마지막 사용량 누락, 0건 성공, 인프라 중단을 검증한다.
- 합계는 원본 이벤트에서 재계산되며, 검수를 두 번 해도 원본 해시와 이전 검수 결과가 바뀌지 않는다.
- 전체 정보를 가진 평가기의 답·품질 판정이 Agent 입력으로 유입되지 않는다.

## F. 문제·회차 계획과 worktree 실행 조정

선행 조건: A·C·E.

대상: `problem.py`, 새 `scheduling.py`, `runner.py`, 실행 계획·설정.

작업:

1. 현재 문제를 개발 자료로 구분하고, 아직 실제 모델 결과를 보지 않은 동일 규모의 확인용 문제 하나를 구조 기준으로 선정한다. 선정 기준·입력·정답의 독립 검산·해시를 실제 실행 전에 고정한다. 삭제한 실행 결과의 재현을 선정 기준으로 삼지 않는다.
2. 기본 실행은 문제 하나에서 방식별 5회다. 문제군 확대·성공 보충 실행은 넣지 않는다.
3. 모든 방식에 대응되는 회차 선발화 `A, B, A, B, A`를 적용한다. 6단계 사전 제안자도 동일하다. 소유 정보는 유지하며 완전한 역할 균형이라고 표시하지 않는다.
4. `RunPlan`에 요청 단계, 반복 번호, 선발화, 문제/설정 해시, 실행 순서·프로필·동시 작업 수를 저장한다. 실행 중 결과에 따라 계획을 바꾸지 않는다.
5. 단독 요청은 해당 단계만 실행한다. 다중 요청은 같은 커밋에서 새 worktree를 준비하고 회차 블록별로 순서를 고정 시드로 배정한다. 기존 결과 폴더를 재사용하지 않는다.
6. 기본 시간 비교는 동시 한 회차, 명시적 병렬 요청은 지정된 동시 실행 프로필로 기록한다. 단계별 작업은 중앙 계획의 해당 슬롯만 가져가며 동일 슬롯을 두 번 실행할 수 없도록 원자적으로 예약한다.
7. 사용자 요청으로 담당 서브에이전트가 실행을 관리하는 경우에도 조정기가 만든 동일 명령과 고정 입력만 사용한다. 담당자의 분석·답·추가 지침을 실험 A·B에게 주지 않는다.
8. 조정기 대기, 세션 초기화, 작업 실행, 결과 저장·정리 시간을 분리한다. 작업 종료 시각과 사용자 요청 전체 경과 시간의 측정 경계를 고정한다.
9. 비교 조건 그룹, 실제 실행 블록, 사후 평가 버전을 구분한다. 단계 번호는 비교 조건 해시에서 제외하되 각 방식 정의 전체는 포함한다. 개별 요청끼리도 동일 문제의 점수는 대조할 수 있지만 같은 블록에서 측정하지 않은 시간은 그 차이를 표시한다.
10. 원본과 중앙 사본의 해시를 확인한다. 신규 모듈·지침·설정·의미 명세가 실행 스냅샷 해시에서 빠지지 않게 파일 목록과 개별 해시를 보존한다.
11. 사용자 묶음 취소는 진행 중인 작업에도 취소 신호를 전달한다. 인프라 오류가 발생하면 새 슬롯 배정을 멈추되 다른 슬롯에서 이미 진행 중인 작업은 자체 종료·사용자 취소까지 보존한다. 명시적 재개는 미실행 슬롯만 대상으로 하며, 실행 여부가 불확실한 슬롯을 자동 재전송하지 않는다.

완료 기준:

- 한 단계는 정확히 5개 계획 슬롯, 여섯 단계는 30개이며 요청 외 단계는 0개다.
- 같은 반복 번호의 문제·정보·선발화가 대응하고, 중단·취소·중복 작업 요청에도 한 슬롯이 다시 실행되지 않는다.
- 이미 시작했다가 중단된 회차와 아직 시작하지 않은 회차를 구분한다. 재개 요청 없이 자동으로 새 시도를 생성하지 않는다.
- 서로 다른 문제·구현·정책·실행 프로필·검수 버전의 측정치를 같은 범위인 것처럼 합치지 않는다.

## G. CLI·사람용 기록·통합 검증

선행 조건: B~F.

대상: `cli.py`, `records.py`, `scripts/export_histories.py`, 문서·통합 테스트.

작업:

5. 신규 기록의 스키마·평가기 버전을 확인한다. 지원하지 않는 버전은 명시적으로 알리고 자동 변환·재채점하지 않는다. 삭제한 과거 결과의 조회·복사·이관 기능은 구현 범위에서 제외한다.
6. `AGENTS.md`, 루트 README, 실험 명세, 운영·검수 안내를 실제 구현에 맞춘다. 구현·오프라인 검증을 통과한 근거와 실제 모델 연결·본실험 대기 상태를 구분해 표시한다.
7. 검증을 통과한 코드·문제·지침·코덱·평가기를 고정한 후 실행 가능한 기본 버전으로 전환한다. 준비 작업이 끝났다는 이유로 실제 실험을 시작하지 않는다.

완료 기준:

- `check`·`status`·`review`·내보내기·결과 비교에서 모델 호출 수가 0이다. 검수·비교 검증에는 새 테스트 자료를 사용한다.

```text
results/readable/<batch-id>/<방식>/<회차>/
  요약.md / 대화.md / 관찰.md / Agent_A.md / Agent_B.md
```

현재 이전할 실험 자료는 없고 `results/`에는 안내 파일만 있다. 위 구조는 구현했으며 새 실행부터 사용한다. 오프라인 테스트 자료는 임시 폴더에서 생성·검증·정리한다. 중간 구현이 실패하면 마지막 검증 상태로 돌아가며, 향후 생성한 실행 원본을 수정해 새 구현에 맞추지 않는다. 사용자가 자료 삭제를 요청하면 그 요청에 따라 정리한다.

실제 모델 연결 점검은 코드 검증과 별도 상태로 남긴다. 연결 점검이 필요하면 기존 운영 규칙과 사용자가 요청한 범위에 맞게 수행하며, 본실험 5회와 합산하지 않는다. 이번 리팩터링에는 실제 모델 호출이 포함되지 않았다.

A~G는 오프라인 검증 범위에서 완료했다. 고정 응답 테스트와 임시 Git 저장소의 worktree 검증이며 실제 모델 성능·연결 성공을 뜻하지 않는다. 실제 실행 이후에는 5회 상태와 사후 내용 검수를 별도로 완료해야 하며, 코드 준비 완료가 곧 일반적인 방식 우열의 증거가 되지는 않는다.

구현 세부 선택: 고정 벡터에는 유한한 과제 의미를 배치하고 메시지 번호는 손실 없는 가변 길이 정수 영역에 둔다. 중단 후 재개는 이전 원본을 바꾸지 않도록 새 파생 실행 폴더를 만들며, 기존 회차는 바이트 그대로 복사하고 미실행 슬롯만 호출한다. 사용자 체크아웃의 HEAD·인덱스를 유지하면서 별도 인덱스로 동일 worktree 커밋을 고정한다.
