# 실험 소개

이 실험은 두 Agent가 같은 일정 문제를 풀 때 소통 방식에 따라 어떤 정보를 보내고, 무엇을 질문하며, 제안을 어떻게 수정하는지 관찰한다. 최종 일정의 품질과 그 과정에서 사용한 시간·모델 비용·전송량을 함께 비교한다.

[문서 안내](README.md) · [가설·과정·결과·인사이트 보고서](experiment-insights-v3-1.md) · [실행 방법](experiment-operation.md)

## Agent가 해결하는 문제

참석자 6명의 회의 3개를 12개 시간대에 배치한다. Agent A는 A1·A2·A3의 참석 가능 시간과 선호 점수를, Agent B는 B1·B2·B3의 정보를 받는다. 상대팀의 비공개 정보는 대화를 통해 알아내야 한다.

| 회의 | 참석자 |
|---|---|
| M1 | A1, A2, B1 |
| M2 | A2, B1, B2 |
| M3 | A1, A3, B2, B3 |

각 회의는 한 시간대에 끝난다. 모든 참석자가 가능한 시간이어야 하고, 공통 참석자가 있는 회의는 겹칠 수 없다. M1은 M3보다 먼저 열려야 한다. 이 조건을 지키면서 전체 참석자의 선호 점수 합계를 최대화하는 것이 목표다. 기록의 슬롯 번호는 0부터 11까지다.

문제는 같은 규모에서 선호가 상충하도록 구성했다. 입력은 [문제 파일](../config/problem.json)에 있으며 모든 방식에 같은 문제를 제공했다. 방식별 다섯 회는 서로 다른 문제가 아니라 같은 문제의 반복 실행이다.

## 여섯 소통 방식

사용자의 ‘1단계’부터 ‘6단계’는 아래 방식 번호다. 순서대로 완료해야 하는 개발 단계가 아니다.

| 번호 | 방식 | 메시지가 전달되는 방법 |
|---|---|---|
| 1 | 자연어 | Agent가 작성한 문장을 그대로 상대에게 전달 |
| 2 | JSON | 공통 필드에 맞춰 작성한 JSON을 그대로 전달 |
| 3 | 논리식·관계 표현 | 정해진 관계식 문법으로 사실·질문·제안을 전달 |
| 4 | 고정 의미 특성 벡터 | JSON으로 작성한 내용을 고정 좌표 배열로 변환해 전송하고, 상대에게 복원된 JSON을 제공 |
| 5 | 바이트코드 | 정해진 명령으로 작성한 내용을 바이너리로 전송하고, 상대에게 복원된 JSON을 제공 |
| 6 | 공동 기호 언어 | 고정 문법에서 사용할 기호 이름을 매회 제안·수락한 뒤 그 기호로 대화 |

모든 방식은 개인 사실, 팀 요약, 구체적인 질문, 후보 일정과 평가, 이전 메시지 재확인, 제안·수정·수락·반려를 지원한다. 원자료를 모두 보낼지, 필요한 요약만 보낼지, 추가 질문을 할지는 Agent가 정한다. 자연어의 자유 표현 전체와 구조화 문법의 표현력이 같다는 의미는 아니다.

3단계에는 자동 증명기가 없다. 4단계는 학습 임베딩이나 모델 내부 상태의 교환이 아니라, 미리 정한 의미를 8,192개 float32 좌표와 별도 정수 참조 영역에 저장하는 구현이다. 5단계의 명령은 메시지 표현이며 운영체제 코드를 실행하지 않는다. 6단계에서 합의하는 것은 기호 이름이고 문법 자체는 고정돼 있다.

## 공통 조건과 환경 분리

| 항목 | 적용한 조건 |
|---|---|
| 모델 | A·B 모두 `gpt-5.6-luna`, 추론 수준 `high` |
| 반복 | 방식별 5회, 총 30회 |
| 대화 세션 | 매회 A·B를 새 세션으로 생성하여 총 60개 세션 사용 |
| 초기 정보 | 같은 문제와 역할별 정보, 공통 행동 규칙 제공 |
| 선발화 | 모든 방식에서 회차 순서대로 A·B·A·B·A |
| 자율성 | 정보 공유·질문·제안·수정 전략과 횟수는 Agent가 선택 |
| 자원 사용 | 연구용 토큰·시간·메시지·행동·사전 합의 횟수 예산 없음 |
| 실행 공간 | 같은 소스 커밋의 단계별 worktree 사용 |
| 이번 실행 | 6개 방식을 병렬 실행하고, 각 방식 내부에서는 5회를 순서대로 진행 |

새 세션은 이전 회차의 대화를 이어받지 않는다. 실험 Agent에게는 자신의 입력과 지정된 소통 경로만 제공하며, 이 문서·정답·사후 평가를 추가로 전달하지 않는다. 실행 중 코드·문제·설정도 바꾸지 않는다.

worktree는 코드와 결과의 작업 공간을 분리한다. 같은 머신·계정·서비스에서 실행하므로 서버 캐시와 서비스 부하까지 격리되는 것은 아니다. 실제 서비스 제한이나 사용자 취소는 종료 사유로 기록한다.

## 합의와 종료

양쪽이 같은 유효 일정을 최종 제출하면 성공이다. 최고 점수에 도달했는지는 별도로 평가한다. 일반 메시지인 `send`는 기존 제출을 유지하고, 전달에 성공한 `revise`는 양쪽 제출을 무효화해 다시 제출하도록 알린다.

최종 일정의 불일치·제약 위반, Agent의 명시적 중단, 사용자 취소, 인프라 오류는 각각 구분한다. 실패한 회차를 빼고 성공할 때까지 다시 실행하지 않는다. 평가 기준은 [지표 읽는 법](metrics.md)에 있다.

## 후속 연구 범위

아래 1~4차는 연구 범위이며, 실행 명령의 1~6단계와 다르다. 현재 완료한 것은 1차 관찰이다.

| 연구 | 확인할 내용 | 상태 |
|---|---|---|
| 1차 | 같은 일정 문제에서 여섯 방식의 행동·성과·비용 | 30회 완료 |
| 2차 | 사람이 읽는 대화·위키·히스토리의 정확성과 이해 가능성, 생성 비용 | 후속 계획 |
| 3차 | 다른 과제와 문제군에서도 관찰이 유지되는지 | 후속 계획 |
| 4차 | 표현·전송·정보 공유·사전 합의의 효과를 각각 분리 | 후속 계획 |

4차에서는 표현 비교 시 공통 의미와 전송 조건을, 전송 비교 시 메시지 내용·수와 복원 후 모델 입력을 고정한다. 정보 공유 비교에서는 표현과 전송을 고정하고 원자료 전체와 필요한 요약을 비교한다. 사전 합의 비교에서는 최종 사전을 같게 두고 바로 제공하는 경우와 제안·수락을 거치는 경우를 비교한다. 현재 관찰에는 이 분리 실험의 결과가 포함돼 있지 않다.
