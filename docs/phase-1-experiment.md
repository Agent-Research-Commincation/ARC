# 1차 실험 명세 · v1

상태: 합의한 방향에 맞춘 실행기·여섯 모듈·v1 기본값 구현 완료. 공통 슬롯 번호표를 보완하고 기본 협업을 매회 새 Luna high A·B 세션으로 5회 실행해 전부 26점 최적해로 성공했다. 오프라인 테스트 55개 통과. 여섯 방식별 전송 검증과 단계별 본실험은 아직 실행하지 않았다. [5회 관찰 분석](basic-observation-five-runs.md).

## 1. 연구 질문

같은 두 Agent가 같은 일정 문제를 해결할 때, 소통 방식에 따라 정보 전달, 협업 과정, 최종 성과와 비용이 어떻게 달라지는지 관찰한다.

메시지의 내용과 진행 순서를 Agent가 스스로 선택하므로, 관찰되는 차이에는 표현 방식과 그 방식에서 선택한 소통 전략의 영향이 함께 포함된다.

## 2. 현재까지 합의한 조건

### 작업과 정보 접근

- 서로 다른 팀의 일정 정보를 가진 두 Agent가 공동 회의 시간표를 작성한다.
- 각 Agent에는 담당 팀의 참석 가능 시간과 선호를 제공한다.
- 회의별 참석자, 소요 시간 등 공통 규칙은 두 Agent 모두에게 제공한다.
- 상대 팀의 비공개 정보는 지정된 소통 채널을 통해서만 얻는다.
- 공동 목표는 필수 조건을 만족하면서 두 팀의 선호 점수 합계를 최대화하는 것이다.

### Agent와 소통 전략

- Codex를 사용하며, 두 Agent 모두 GPT-5.6 Luna (`gpt-5.6-luna`), 추론 수준 `high`로 고정한다. 각각 독립된 대화 상태를 갖는다.
- 전달할 내용과 질문·제안·수정의 순서는 Agent가 스스로 정한다.
- 전체 정보를 한 번에 전달하거나, 필요한 정보를 질문하며 조율하는 전략을 모두 허용한다. 후보별 표현 규칙은 별도로 정한다.
- 모든 방식에서 문제, 초기 정보 배분과 공통 도구 접근 조건을 맞춘다.

### 고정 모델과 Codex 실행 설정

| 항목 | 확정한 값 |
|---|---|
| 실행 도구 | Codex |
| Agent A 모델 | `gpt-5.6-luna` |
| Agent B 모델 | `gpt-5.6-luna` |
| 두 Agent의 추론 수준 | `high` |
| 적용 범위 | 모든 비교 방식과 각 방식의 5회 실행 |

사용자가 지정한 'GPT Luna high'를 현재 모델 식별자와 추론 설정으로 기록했다. 모델 식별자와 `high` 지원은 [OpenAI 공식 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.6-luna), Codex 설정 키는 [공식 설정 문서](https://learn.chatgpt.com/docs/config-file/config-reference)에서 확인했다(2026-09-08).

실행 설정은 `config/experiment.json`에 저장하고 Codex App Server 세션 생성과 매 턴에 명시적으로 전달한다. 전역 Codex 설정은 수정하지 않는다.

```toml
model = "gpt-5.6-luna"
model_reasoning_effort = "high"
```

Codex App Server를 통해 매회 새 프로세스와 두 개의 독립 세션을 만든다. 로컬에서 확인한 CLI 버전은 `0.153.4`이다. 구조화된 턴 응답에서 선택한 메시지만 상대에게 전달하고, 사용량·상태 이벤트를 수집한다. 실제 반환된 모델·추론 수준과 지침 파일 목록을 검사한다.

모델 설정 외에도 Codex 버전, 실제 적용 설정, 실행 시각, 추가 지침과 도구 접근 범위를 기록하고 본실험 동안 동일하게 유지하는 것을 측정안에 포함한다. 모델 식별자를 고정한 것과 서버의 특정 모델 스냅샷까지 고정한 것은 구분하며, 노출되는 버전 정보만 기록한다.

### 5회 반복과 새 세션

- 자연어, 정해진 JSON 구조, 논리식·관계 그래프, 의미 벡터, 바이트코드, Agent 공동 언어를 각각 1~6단계로 고정한다.
- “N단계 해줘” 요청은 `python3 lab.py run N`에 연결한다. 해당 단계만 실행하며 다른 단계를 자동으로 이어 실행하지 않는다.
- 각 소통 방식마다 5회 실행한다.
- 모든 방식과 반복 실행에 동일한 일정 문제와 초기 정보를 제공한다.
- 1회 실행은 Agent A와 Agent B를 각각 새 세션으로 시작하는 하나의 협업 실험이다.
- 매 실행에서 대화 기록과 작업 상태를 초기화한다. 이전 실행의 대화나 결과를 다음 실행에 전달하지 않는다.
- 사용자가 말한 '다른 환경'은 새 세션을 의미한다. 서로 다른 문제 5개나 서로 다른 모델·실행환경을 의미하지 않는다.
- 방식별 규칙이나 사전 준비 상태는 본실험 중 실행 결과를 보고 바꾸지 않는다. 공동 언어의 합의·학습 범위는 별도로 정의해야 한다.

## 3. 합의한 핵심 지표와 평가 우선순위

| 순서 | 핵심 지표 | 확인할 질문 |
|---|---|---|
| 1 | 과제 성공률·결과 품질 | 5회 중 몇 회가 모든 필수 조건을 만족했으며, 유효한 시간표의 선호 점수가 최적해와 얼마나 차이 나는가? |
| 2 | 성공 1건당 총비용 | 실패한 실행까지 포함하면 성공 1건을 얻는 데 얼마의 비용이 들었는가? |
| 3 | 전체 완료 시간 | 작업 시작부터 최종 결과 제출까지 실제로 얼마나 걸렸는가? |
| 4 | 실제 통신량 | 두 Agent 사이의 채널에서 실제로 전송한 데이터는 얼마나 되는가? |
| 5 | 통신 처리 비용 | 메시지를 만들고 변환·검증·해석하는 데 별도로 식별할 수 있는 비용은 얼마나 되는가? |

성공 여부와 품질을 먼저 확인한 뒤 비용과 시간을 비교한다. 비용이 낮거나 실행이 짧다는 이유만으로 실패한 실행을 우수하다고 평가하지 않는다.

메시지 수, 재질문과 제안 수정 과정은 다섯 핵심 지표를 설명하는 보조 지표로 유지한다.

## 4. 지표 측정안

이 절은 v1 측정 정의다. 실제 실행에서 측정 불가능한 값은 0 대신 `null`로 표시한다. 원자료와 부분 추정값을 구분해 기록한다.

### 1. 과제 성공률·결과 품질

- 평가기는 전체 입력을 가지고 최종 시간표의 모든 필수 조건을 검사한다. Agent에는 담당 범위의 입력만 제공한다.
- 성공률은 `성공한 실행 수 / 5`로 계산하고, 성공 횟수와 각 실행의 성공·실패도 함께 남긴다.
- 시간표 선호 점수는 사전에 고정한 규칙으로 계산한다. 최적 점수는 프로그램으로 구해 둔다.
- 유효한 시간표에 대해 `최적 점수 - 제출 점수`를 기록한다. 0이면 최적해이다.
- 유효하지 않은 시간표나 미완료 실행은 실패로 표시하고, 유효한 결과의 품질 점수와 구분한다.

### 2. 성공 1건당 총비용

- 방식별 성공 1건당 총비용은 `해당 방식의 5회 실행 총비용 / 해당 방식의 성공 횟수`로 계산한다.
- 실행 총비용에는 두 Agent의 모델 호출, 작업 수행 도구와 소통에 필요한 변환·해석·실행 처리를 포함한다. 각 비용 항목은 한 번만 합산한다.
- 사전 학습이나 장치 준비에 드는 일회성 비용은 실행당 비용과 구분해 기록한다. 이를 실행당 비용으로 배분할지는 구현 선택 후 정한다.
- 실패하거나 중단된 실행의 비용도 포함한다.
- Codex 실행에서 확인할 수 있는 입력·출력·캐시 토큰 등의 사용량을 원자료로 보존한다. 금액으로 환산할 경우 실제 청구액과 단가 기반 추정액을 구분하고, 확인할 수 없는 항목은 미측정으로 표시한다. 구체적인 과금·사용량 수집 경로는 실행 방식과 함께 정한다.
- 성공이 0회이면 성공 1건당 총비용은 계산 불가로 표시하고, 5회 총비용과 실패 횟수를 보고한다.
- 로컬 CPU 단가는 기본 미설정이다. 이 경우 총비용은 미측정이며 모델 비용만의 부분 추정을 별도로 보고한다. CPU 단가를 설정하면 실행기와 종료된 Codex 자식 프로세스의 CPU 사용량을 합산한다.
- 인프라 오류로 5회를 완료하지 못한 묶음은 미완료로 표시하고 성공률과 성공 1건당 비용을 계산하지 않는다.

### 3. 전체 완료 시간

- 각 1회 실행의 App Server 초기화·세션 생성부터 최종 결과 제출 또는 실행 중단까지의 실제 경과 시간을 측정한다. 언어 합의·통신 처리·응답 대기도 포함한다.
- 병렬로 동작하는 두 Agent의 시간을 단순 합산하지 않는다.
- 실패·중단까지 걸린 시간은 성공한 실행의 완료 시간과 구분해 표시한다.
- 평가기 실행 시간과 본 작업 시간은 구분해 기록한다.
- 방식별로 5회 각각의 시간과 요약값을 제시한다. 5회 실험 전체를 운영하는 데 걸린 시간은 회차 사이 대기 등이 포함되는 별도 운영 지표로 구분한다.

### 4. 실제 통신량

- 각 실행에서 두 Agent 사이의 채널을 양방향으로 통과한 직렬화된 메시지의 바이트 수를 합산한다. 재전송도 실제 전송한 횟수만큼 포함한다.
- 관측 경계는 로컬 메시지 전달 채널이다. 실제 직렬화 프레임의 4바이트 헤더 길이·공통 JSON 헤더·방식별 본문을 측정한다. 로그의 Base64 저장 크기와 모델 API 네트워크 트래픽은 이 지표에 포함하지 않는다.
- 벡터나 바이트코드를 텍스트로 감싸 전송하면 포장된 실제 전송 크기를 측정한다. 원래 벡터의 차원 수나 디코딩한 크기를 실제 통신량으로 대신하지 않는다.
- 모델이 처리한 토큰 수는 전송 바이트 수와 별도로 기록한다.

### 5. 통신 처리 비용

- 메시지 생성·변환, 직렬화·역직렬화, 형식 검증, 수신 메시지 해석에 사용하는 모델 호출과 처리 장치의 비용을 식별해 기록한다.
- 방식별로 추가되는 벡터 변환·해석, 바이트코드 해석, 공동 언어 인코딩·디코딩 등의 처리도 해당 범위에 포함한다. 사전 학습·장치 준비의 일회성 비용은 별도 내역으로 유지한다.
- 한 번의 모델 호출이나 코드 실행이 작업 추론과 통신 처리를 함께 수행하면 비용을 임의 비율로 나누지 않는다. 해당 비용은 총비용에 한 번 포함하고, 통신 부분은 분리 측정 불가로 표시한다.
- 분리 측정한 통신 처리 비용은 총비용의 부분 내역이다. 총비용에 다시 더하지 않으며, 분리 측정 불가한 항목이 있으면 그 범위도 함께 보고한다.
- 처리 시간과 토큰·연산 사용량을 원자료로 함께 남긴다. 처리 시간은 금액과 별도 단위이며, 전체 완료 시간에 다시 합산하지 않는다. 금액을 확인하거나 환산할 수 없는 항목은 미측정으로 표시한다.

### 보조 지표: 소통 과정

- 메시지 수를 기록한다. 메시지 1개의 경계는 모든 방식에서 일관되게 정의한다.
- 재질문, 일정 제안, 충돌 지적, 제안 수정과 최종 합의 과정을 원본 메시지 및 해석 결과와 연결해 검토한다.
- 서로 다른 표현 방식의 과정 지표를 어떻게 같은 기준으로 판정할지는 추가로 정한다.

### 결과 표현과 해석

- 방식마다 5개 실행의 원자료를 보여주고, 다섯 핵심 지표의 결과와 필요한 요약값을 함께 제시한다. 성공 1건당 총비용은 5회 전체를 합산해 계산한다.
- 성공한 결과의 품질을 비교할 때 각 방식의 성공 횟수도 함께 표시한다.
- 품질이 다른 결과의 비용과 시간을 비교할 때는 그 품질 차이를 명시한다. '비슷한 품질'의 허용 범위는 선호 점수 체계를 정한 후 정의한다.
- 같은 문제에서 새 세션으로 반복한 결과이므로 실행 간 차이를 관찰할 수 있다. 5회만으로 변동성을 정밀하게 추정하거나 다른 작업으로 일반화하지 않는다.
- 단일 종합 점수나 보편적인 순위를 전제하지 않는다.

## 5. v1 고정 일정 문제

| 항목 | 기본값 |
|---|---|
| Agent별 담당 인원 | 각 3명, 총 6명 |
| 회의 수 | 3개 |
| 시간 범위 | 2일, 하루 6개의 1시간 슬롯 |
| 회의 길이 | 각 1슬롯 |
| 회의 참석자 | 회의마다 지정하며, 각 회의에 두 팀의 참석자가 모두 포함됨 |
| 필수 조건 | 참석자 전원 참석 가능, 같은 참석자의 회의 중복 금지, 지정된 회의 간 선후 관계 |
| 선호 | 참석자별·시간대별 0~3점. 각 회의 참석자의 점수를 합산 |

`config/problem.json`에 고정 데이터를 저장했다. M1은 A1·A2·B1, M2는 A2·B1·B2, M3는 A1·A3·B2·B3가 참석하며 M1이 M3보다 먼저 열려야 한다. 가능한 배치를 모두 검증하면 유효한 시간표 54개와 최적 점수 26점이 나온다. 이 정답은 평가기만 사용하며 Agent 입력에 넣지 않는다.

## 6. v1 실행 규칙과 후속 확인

- A부터 번갈아 기회를 제공한다. 메시지 내용·질문·제안·수정 전략은 Agent가 정한다.
- 모든 방식의 공통 입력에 0~11 슬롯 ID와 시간의 대응표를 제공하며, 가능 시간·선호 배열의 인덱스 및 메시지·제출의 ID가 일치함을 명시한다.
- 두 Agent가 각각 동일한 시간표를 제출해야 합의로 본다. 전역 필수 조건을 만족해야 성공이다.
- 회차당 600초, 호출당 120초, 작업 기회 24회, 메시지 20개, 본문 16,384바이트가 기본 상한이다. 누적 토큰 100,000은 호출 완료 후 확인한다.
- 6단계의 언어 합의는 최대 6회의 별도 기회로 진행하고 시간·메시지·비용은 회차 총량에 포함한다.
- 과제 실패는 다음 회차로 진행하고, 인프라 오류는 묶음을 미완료 상태로 중단한다. 실패를 숨기는 자동 재실행은 하지 않는다.
- 여섯 모듈의 구체적인 표현·해석 규칙, 정보 분리와 기록 형식은 [실행 운영 문서](experiment-operation.md)에 있다.
- 실제 모델 응답을 이용한 전송 검증, 과제의 협업 난이도 확인, 별도 기준 구성과 로컬 비용 단가 설정은 후속 항목이다. 자연어를 자동으로 기준 구성으로 삼지 않는다.

여섯 단계를 각각 5회 실행하면 총 30회이다. 사용자가 요청한 단계부터 개별 실행하며, 별도 기준 구성을 추가로 실행하는 경우 그 실행 횟수는 따로 정한다. 구현 구조와 요청 처리 규칙은 [요청 기반 실험 운영](experiment-operation.md)을 참고한다.
