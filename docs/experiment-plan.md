# 여섯 소통 방식 실험 계획

**AI끼리 소통할 때 어떤 방법이 효율적일까?** 같은 문제를 여섯 방식으로 각각 30회 해결하게 하고, 실제 대화와 결과를 함께 살펴본다. **1차 본실험 180회 실행을 완료했다.** 이 문서는 실행 전에 정한 가설과 관찰 기준을 보존하며, 실제 결과와 해석은 [실험 보고서](experiment-report.md)에서 다룬다. 아래 기대는 관측 결과를 뜻하지 않는다.

## 1. 프로젝트 가설

효율은 결과 품질과 함께 모델 비용·완료 시간·전송량·통신 처리를 보고 판단한다. 빨리 합의하거나 작게 보냈다는 사실만으로 가장 효율적인 방식이라고 정하지 않는다.

| 단계 | 확인하려는 질문 | 기대하는 효과 |
|---|---|---|
| 1 · 자연어 | 자연어로 소통하는 게 효율적인가? | 필요한 정보를 문장으로 설명하면 적은 사용량과 시간으로 정확한 합의에 도달할 수 있다. |
| 2 · JSON | 정해진 JSON 항목으로 소통하는 게 효율적인가? | 사실·질문·후보를 구분하면 상대가 정보를 확인하고 결정을 내리기 쉬울 수 있다. |
| 3 · 논리식·관계 표현 | 사실과 관계를 논리식으로 표현하는 게 효율적인가? | 관계를 명시하면 간결하게 전달하면서 해석의 모호함을 줄일 수 있다. |
| 4 · 고정 의미 특성 벡터 | 정보를 정해진 숫자 배열로 전달하는 게 효율적인가? | 고정 좌표로 정보를 변환·복원하는 방식이 전송과 처리에 유리할 수 있다. |
| 5 · 바이트코드 | 짧은 명령을 바이너리로 바꿔 소통하는 게 효율적인가? | 같은 의미를 적은 바이트로 전달해 전송 부담을 줄일 수 있다. |
| 6 · 공동 기호 언어 | Agent끼리 기호를 합의한 뒤 소통하는 게 효율적인가? | 합의한 기호로 대화가 간결해지면 사전을 정하고 사용하는 부담을 상쇄할 수 있다. |

이는 관찰을 위한 가설이다. 30회라는 수만으로 통계적 충분성이나 보편적인 우열이 보장되지는 않는다. 각 방식에서 지침·표현·공유 정보·전송 처리가 함께 달라질 수 있으므로, 표현 하나의 효과를 분리하는 것은 [4차 연구](../README.md)의 범위다.

## 2. 공통 문제와 각 단계의 과정

### 두 팀의 회의 담당자가 일정을 정한다

회의 담당자 두 명이 각자 자기 팀의 일정만 알고 있다고 생각해 보자. 한쪽이 가능한 시간을 알려 주면 다른 쪽은 자기 팀의 정보와 맞춰 보고, 후보를 제안하거나 추가로 질문해야 한다. 둘은 모두 참석할 수 있는 일정 중 참석자들이 가장 선호하는 일정을 찾아야 한다.

Agent A는 A1·A2·A3, Agent B는 B1·B2·B3의 참석 가능 시간과 선호만 받는다. 총 12개 시간대에 다음 세 회의를 배치한다.

| 회의 | 참석자 |
|---|---|
| M1 | A1, A2, B1 |
| M2 | A2, B1, B2 |
| M3 | A1, A3, B2, B3 |

모든 참석자가 가능한 시간이어야 한다. 공통 참석자가 있는 회의는 겹치면 안 되고, M1은 M3보다 먼저 열려야 한다. 참석 가능 여부와 선호는 서로 다른 정보다. 열 수 있는 일정이라도 더 선호하는 대안이 있을 수 있다.

### 모든 방식에서 지키는 진행 순서

1. 매회 새 A·B 세션에 공통 규칙과 자기 팀의 비공개 정보를 제공한다.
2. Agent가 무엇을 공유·질문·제안·수정할지 선택한다. 6단계는 먼저 기호 사전을 합의한다.
3. 실행기가 해당 방식의 메시지를 전달한다. 문법 오류는 전달 전에 거절하지만 내용의 정답을 대신 알려 주지 않는다.
4. 양쪽의 최종 제출을 받은 뒤 일치 여부와 일정 유효성을 판정한다. 진행 포기·취소·인프라 중단도 기록한다.
5. 종료 후 최적성과 대화 내용의 정확성을 별도로 검수한다. 정답과 사후 검수 내용은 실험 Agent에게 전달하지 않는다.

아래는 각 방식에서 가능한 소통 경로이며 실제 관측한 대화 사례가 아니다. 자료 교환 횟수나 제안·수락 순서를 강제하지 않는다.

| 단계 | Agent가 작성하고 상대가 읽는 과정 | 대화에서 살펴볼 내용 |
|---|---|---|
| 자연어 | 문장·목록으로 일정 정보를 작성하고 상대가 그대로 읽는다. | 어떤 정보를 요약했는지, 후보의 근거를 설명하거나 확인하는지 |
| JSON | 사실·요약·질문·후보를 정해진 항목에 작성하고 상대가 같은 JSON을 읽는다. | 항목별 자료를 공유하는 범위와 추가 질문·수정 |
| 논리식·관계 표현 | 정해진 관계식으로 작성하고 상대가 같은 관계식을 읽는다. | 관계 표현을 올바르게 쓰는지, 자신의 제약과 상대 정보를 함께 반영하는지 |
| 고정 의미 특성 벡터 | JSON 작성 → 고정 좌표 숫자 배열로 전송 → JSON으로 복원해 읽는다. | 모델의 대화 행동과 숫자 배열의 전송·변환 부담을 각각 확인 |
| 바이트코드 | 짧은 명령 작성 → 바이너리로 전송 → JSON으로 복원해 읽는다. | 전송 크기와 모델이 실제로 읽는 자료·누적 대화량 |
| 공동 기호 언어 | 고정 문법 위에서 기호 사전을 합의하고 그 기호로 관계식을 주고받는다. | 합의 비용, 사용 중 문법 오류와 재시도, 후보의 수정 |

4단계는 학습 임베딩이나 모델 내부 잠재 상태 교환이 아니다. 6단계는 새로운 문법 자체를 발명하는 실험이 아니다. 회의별 팀 요약은 해당 회의에 참석하는 자기 팀 사람들의 가용성과 선호 합계를 뜻한다.

## 3. 실험 결과

**방식별 30회, 총 180회 실행 완료.** 집계값과 해석은 [실험 보고서](experiment-report.md), 실제 발화와 제출·판정 근거는 [회차별 대화 기록](../result/20260912T170838Z-plan-22772406666b/README.md)에 연결한다. 아래는 실행 전에 정한 결과 보고 항목이다. 실패를 성공으로 바꾸거나 미측정 항목을 0으로 표시하지 않는다.

| 평가 항목 | 결과 보고 방식 |
|---|---|
| 과제 성공률·결과 품질 | 같은 유효 일정에 합의한 회차, 가장 선호하는 일정에 도달한 회차, 실패·중단·미실행을 구분 |
| 성공 1건당 총비용 | 측정 가능한 비용 범위와 미측정 항목을 명시하고 모델 비용 추정을 별도 보고 |
| 전체 완료 시간 | 회차별 경과 시간과 평균·중앙값·최소·최대; 성공 회차와 모든 회차를 구분 |
| 실제 통신량 | 본문·헤더와 합계, 송신·수신 텍스트 크기, 메시지 수 |
| 통신 처리 비용 | 인코딩·디코딩·전달 준비의 로컬 CPU 시간, 복원 오류, 측정 가능한 금액 |
| 실제 대화 과정 | 첫 제안, 추가 질문, 후보 수정, 수락, 최종 제출을 원문과 함께 제시 |

내용 정확성은 선택한 검수본의 범위·검토자와 함께 확인한다. 자연어 검수를 끝내지 않은 자료는 검수 대기로 남긴다. 같은 설정·문제·코드·실행 프로필의 결과를 비교하고, 실패를 제외해 성공 30회를 채우지 않는다.

## 4. 핵심 인사이트 도출 기준

관측 결과에 대한 해석과 한계는 [실험 보고서](experiment-report.md)에서 확인한다. 아래는 실행 전에 정한 인사이트 도출 질문이며, 실제 대화와 전체 반복 결과에 근거해 답한다.

- 어떤 방식이 비용·시간·전송량에서 유리했으며, 회차마다 얼마나 달랐는가?
- 처음 제안부터 좋은 일정이었는가, 잘못된 후보를 수정한 뒤 도달했는가?
- 오류가 있는 후보를 상대가 그대로 수락한 경우와 수정한 경우는 각각 얼마나 있었는가?
- 추가 질문 전에 이미 올바른 후보가 있었는가? 대화 후 실제로 무엇이 바뀌었는가?
- 작은 전송량이 모델 사용량 감소와도 함께 나타났는가?
- 기호 사전의 합의와 사용 중 재시도는 각각 어느 정도 부담이었는가?

행동의 빈도는 전체 회차 중 몇 회인지, 오류가 생긴 회차 중 몇 회인지 분모를 명시한다. 자동 관찰표와 원문을 함께 검수하며, 내부 생각이나 수락의 숨은 이유를 추측해 채점하지 않는다. 대표 사례만 골라 일반화하지 않고 반대 사례와 전체 반복 결과를 함께 보여 준다.

“이 조건에서 이런 과정과 결과가 반복됐다”는 관찰과 “이 표현 때문에 차이가 났다”는 원인 설명을 구분한다. 같은 문제의 반복만으로 다른 과제나 장기간 협업의 효과까지 확정하지 않는다.
