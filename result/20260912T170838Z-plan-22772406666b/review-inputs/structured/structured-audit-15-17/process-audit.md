# 2~6단계 trial15~17 추가 과정 감사

15회 모두 첫 전체 후보와 최종 제출이 `(M1,M2,M3)=(1,6,10)`, 유효·20점이다. 자동 내용 판정은 **정답 2,163 / 오류 0 / 보류 0**이다. 불가능·미최적 후보, 후보 변경 및 명시 `revise`는 없었다. 전달된 task 메시지는 49개이며 코덱 오류는 0건이다. 전달 전 프로토콜 거절 12건은 별도로 기록한다.

## 새로 확인한 과정

**2단계 trial16·5단계 trial15 — 한쪽 제출 후 wait, 별도 수락 메시지 뒤 양쪽 제출.** 두 회차 모두 request-3에서 한쪽이 먼저 제출했고, request-4에서 상대가 `wait`했다. request-5에서 이미 제출한 Agent가 같은 일정의 `accept`를 `send`하고, request-6에서 상대가 제출했다. 2/16은 B가 먼저 제출하고 A가 기다렸으며, 5/15는 A가 먼저 제출하고 B가 기다렸다. 기존 제출 상태는 wait와 send 동안 유지됐다. `accept`가 없었다가 나중 전달된 순서는 관찰 사실이고, 내부 의도나 wait의 필수성을 추론하지 않는다. 조기 종료·미제출 종료는 없으며 이 wait를 실패로 분류하지 않는다.

**3단계 trial15 — 요약 질문의 반복 거절 이후 개인 자료를 요청.** B가 m2에서 후보만 보낸 뒤, A의 `asksumMARY`(두 번), `asksummmary`, `asks ummary` 질문이 request-3~6에서 거절됐다. 이후 A는 m3에서 후보 슬롯에 해당하는 B 개인 가용성·선호도 10개를 `askfact`로 요청했고 B가 m4에서 모두 답했다. A는 다시 m5에서 B1~B3의 모든 슬롯에 대한 개인 자료 72개를 요청했고 B가 m6에서 모두 답했다. 그 뒤 양쪽 제출이다. 요약 질문의 오타를 고쳐 같은 질문을 전달한 사례가 아니라 **실제 후속 요청의 종류와 범위가 바뀐 사례**다. m4의 10개는 m6에서 다시 나타나므로 내용 154개는 중복을 포함한 발생 수다.

**3단계 trial16 — 상대가 자기 팀 가용 슬롯에 해당하는 부분 요약을 요청.** B는 m3에서 A 팀 요약 54개를 요청했고 A가 m4에서 정확히 해당 54개에 답했다. 요청 슬롯 집합이 원본 문제에서 B 팀이 가능한 회의별 슬롯 집합과 같음을 별도 확인했다. 첫 거절(request-3)의 `availability`를 `available`로 바꾼 것 외에 적용 요청 내용이 그대로인 것도 문자열 대조했다. 생략된 슬롯을 불가 주장으로 추가하지 않았다.

**4단계 trial16 — 후보 슬롯 요약 6개를 받은 뒤 전체 72개를 추가 요청.** A의 m2에는 후보와 그 세 슬롯의 A 팀 가용성·선호도 6개가 있다. B는 m3에서 A 팀 전체 요약 72개를 요청했고 A가 m4에서 모두 답했다. 이 6개는 오류 교정 대상이 아니라 정확한 정보의 반복이다. 4단계는 고정 의미 특성 벡터 구현이다.

**3단계 trial17 — 비ASCII 문자가 섞인 술어를 수정.** B의 request-6은 `teამavailable(B,M1,0,1).`에서 거절됐다. 원문에는 이 형태와 `teамavailable` 형태가 섞여 있다. 다음 적용 응답 m4는 모두 `teamavailable`이다. 문자열 검산으로 술어 치환 외에 수치·나머지 내용이 같음을 확인했다. 이 사례를 데이터 값 오류로 세지 않았다.

**6단계 trial16·17 — 합의 기호와 기본 이름의 혼용을 수정.** 두 회차의 사전에는 `askvalid→aval`, `askscore→ascore`가 있다. request-5에서 기본 이름을 사용한 응답이 `askvalid(1,6,10)`에서 거절됐고, 다음 m5는 두 기호만 합의한 이름으로 바뀌었다. 상대는 m6에서 유효·20점을 명시하며 수락했고 양쪽 제출했다. 내부 의미를 새로 학습했다는 해석은 하지 않는다.

## 검산 범위와 산출물

- 같은 고정 `write_trial_records` 및 `observation-review-v3.1`로 15회 전체를 임시 출력에 재계산했다. 49개 task의 정규화 결과, 코덱/프레이밍, 명시 주장과 후보, 99개 제어 이벤트를 자동 대조했다. 질문 572개는 사실 주장으로 세지 않는다. 코덱 오류 0은 **전달된 메시지**에 대한 결과이며 위 거절 12건을 상쇄하지 않는다.
- 직접 원문 독해는 **task 23/49개**: 2/16 m3, 5/15 m3, 3/15 m2~6, 3/16 m2~4, 3/17 m1~4, 4/16 m2~4, 6/15 m3~4, 6/16·17 m5~6이다. 거절 응답 12개 전체, 두 wait 회차의 request-3~6, 6/15 setup 수락 request-3, 단계6 세 회차 사전도 읽었다. 나머지는 자동대조·정규화 결과 검토 범위이며 완전 수동 전수검수는 아니다.
- 평가기 산술 함수를 쓰지 않고 전체 후보 22개·최종 15개와 추출된 내용 주장 **2,163개(개인 사실 442, 팀 요약 1,716, 일정 점수 3, 유효성 2)**를 원본 문제에서 다시 계산했다. 모두 일치했다. 주장 추출은 기존 파서 결과를 사용했으므로 추출 자체까지 독립 검증한 것은 아니다. 1,728개 배정 중 유효 54개, 유일 최적 일정 20점도 확인했다.
- 일부 요청의 질문키와 후속 응답키 일치, 기호만 바뀐 거절 후 수정, wait 중 제출 상태 보존을 별도 검산했다. 모든 선택 원본 파일과 실행 소스 해시는 전후 동일하고 단계별 평가 소스도 동일하다. 설정 수정과 추가 모델 호출은 없었다. 방식의 순위나 인과 효과를 일반화하지 않는다.
