# 2~6단계 trial21~22 추가 감사

10회 모두 최종 `(M1,M2,M3)=(1,6,10)`, 유효·20점이다. 내용은 **정답 1,440 / 오류 2 / 보류 0**, 전달된 task 메시지는 25개, 코덱 오류는 0건이다. 3/21의 최초 후보는 유효·19점이었고 이후 20점으로 변경됐다. 불가능 후보는 없었다.

## 결과와 별개로 남은 내용 오류

|원문 위치|실제 주장 → 원본 기대값|원본 근거 및 후속 상태|
|---|---|---|
|2/22 m2 A|`preference/A/M3/3: 2 → 1`|M3의 A 참석자는 A1·A3이고 슬롯3 선호도는 각각 1·0이다. 이후 peer 메시지가 없고 양쪽 제출만 이어져 명시 정정 없음.|
|6/22 m3 B|`tpref(B,M3,4,3).` → 기대값0|M3의 B 참석자는 B2·B3이고 슬롯4 선호도는 각각 0·0이다. 이후 A 요약, B 제안, A 수락에는 이 B 요약키 정정이 없음.|

두 메시지는 해당 슬롯의 팀 가용성이 0인 점을 정확히 전달했다. 기대 선호도는 **원본 선호도 합계**로 산출했으며, 불가 슬롯이라는 이유로 0으로 간주하지 않았다. 실제로 첫 오류의 기대값은 1이다.

기존 단일 오류 반사실 검산은 두 오류 모두 유효 일정·점수·최적점수·최종 제출을 바꾸지 않는 것으로 판정했다. 독립 열거에서도 M3가 해당 슬롯에 놓이는 유효 일정이 없었다. 이는 이번 문제의 최종 결과 영향에 관한 관찰이며, 두 주장을 정답 처리하거나 정정됐다고 기록할 근거가 아니다.

## 후보 변경과 제어 흐름

**3/21:** B는 m2에서 `(9,6,10)`을 제안했다. A는 m3/request-4에서 `revise`로 `(1,6,10)`을 보냈고 양쪽 제출로 끝났다. 독립 점수는 19→20이다. 두 메시지는 점수·최적성 주장을 명시하지 않았다. revise는 첫 제출 전에 발생해 `cleared_agents=[]`이며, 기존 제출을 삭제한 사례가 아니다.

**6/21:** B의 m4는 B 요약 72개와 최적 후보, 그 후보의 유효성·점수 질문을 포함한다. A는 request-5에서 먼저 제출했고 B는 request-6에서 wait했다. A는 request-7/m5에서 `accept().`, `valid(1,6,10,1).`, `score(1,6,10,20).`를 보내고 B가 request-8에서 제출했다. 제출 상태는 wait와 send 동안 유지됐다. 이 수락 메시지에는 `at` 일정 필드가 없으므로 새 전체 후보로 추가 세지 않았다. 명시 평가 두 건은 해당 일정에 대한 주장으로 따로 검산했다.

전체 task 제어는 `send 24 / submit 20 / revise 1 / wait 1`이다. setup 적용4개와 거절3개를 합쳐 제어 응답53개다. stop이나 미제출 종료는 없었다.

## 문법 거절 후 달라진 실제 메시지

|범위|기록된 거절|적용된 후속 행동|
|---|---|---|
|3/21 request-1|`Only one message kind`|A가 `inform()`과 `request()`를 함께 넣은 응답이 거절됐다. 다음 m1은 자기 팀 요약만 유지하고 요청 부분을 제거했다. 해당 정보 부분의 동일성을 문자열 대조했다. 원문의 `availability` 인수 문제를 별도 거절로 중복 계산하지 않음.|
|3/22 request-1|알 수 없는 술어 `asksum mary(preference,A,M1,0)`|다음 시도도 아래 오타로 거절됨.|
|3/22 request-2|알 수 없는 술어 `asks ummary(available,A,M1,0)`|B는 질문을 전달하지 않고 자기 요약72개만 m1로 보냈다. A는 m2에서 자기 요약72개와 후보를 보내고 B가 m3에서 수락했다.|

3/22에서는 **적용된 질문이 0개**다. 따라서 “요약 질문의 철자를 고쳐 답을 받았다”가 아니라 “두 질문 시도가 거절된 뒤 정보 교환과 제안으로 이어졌다”가 원문에 맞다. 거절3건은 모두 task 구간이며 6단계 사전 합의·사용에는 거절이 없다.

## 검산·직접 독해 범위

- 같은 고정 평가기로 task25개·제어응답53개를 자동 대조했다. 질문290개와 생략 정보는 사실 주장으로 승격하지 않았고 전달 전 거절을 전달된 코덱 오류와 구분했다.
- 직접 읽은 task 원문은 **15/25개**: 2/22 m1~2, 3/21 m1~3, 3/22 m1~3, 6/21 m3~5, 6/22 m3~6. 거절 응답3개 전체, 3/21 revise 응답, 6/21 request-5~8과 단계6 두 사전도 읽었다. 나머지는 자동대조·정규화 검토이며 완전 수동 전수검수는 아니다.
- 추출된 주장1,442개(요약1,440·일정 점수1·유효성1), 전체 후보13개·최종10개를 기존 평가기 산술 함수를 쓰지 않고 원본 문제로 다시 계산했다. **정답1,440·오류2**와 일치했다. 오류키의 후속 재진술 부재, 요청·응답 키 일치, 제출 상태 보존도 확인했다. 추출 자체는 기존 파서를 사용했다.
- 1,728개 배정 중 유효54개·유일 최적20점을 확인했다. 선택 원본 파일과 실행 소스 해시는 전후 동일하며 단계별 평가 소스도 같다. 코어·설정·원본 수정과 추가 모델 실행은 없었다. 방식의 우열·비용 순위 일반화는 범위 밖이다.
