# 2~6단계 trial25~26 추가 감사

10회 중 **9회는 유효·20점, 6/25는 같은 무효 일정을 양쪽이 제출해 실패**했다. 인프라 상태는 모두 normal이다. 내용 주장 발생 수는 **정답 1,439 / 오류 6 / 보류 2**, task 메시지는 29개다. 전달된 코덱 오류는 0건이며 별도 거절은 5건(setup1·task4)이다.

## 6/25: 잘못된 가용성 전달 뒤 무효 일정 수락·제출

|적용된 메시지|내용|
|---|---|
|m3 A|A 요약 72개. 모두 맞음.|
|m4 B|B 요약 72개. `tavail(B,M1,8,1).`와 `tavail(B,M2,8,1).` 두 값이 틀림. 원본은 둘 다 0.|
|m5 A|`(M1,M2,M3)=(8,6,10)` 제안.|
|m6 B|같은 일정 수락.|

B1은 슬롯8에 불가하며 M1·M2 모두에 참석한다. 이후 두 요약을 교정하거나 B1의 불가를 지적한 task 문장은 없다. A request-11과 B request-12가 모두 `(8,6,10)`을 제출했고, 결과는 `Final schedule violates hard constraints`, 위반은 `Unavailable: B1 at M1`이다. 최종 공식 점수와 quality gap은 미정의이며 0점으로 바꾸지 않았다. 처음 전달된 전체 후보부터 무효였고 후보 변경·revise·wait·stop 없이 종료됐다.

오류의 독립 산술 대입 결과는 다음과 같다. 각 행은 원본 문제에서 해당 요약만 바꾼 결과다.

|대입한 오류|가능 일정 수|대입 후 최적|실제 제출의 유효성 변화|
|---|---:|---|---|
|B·M1·슬롯8 가용성 0→1|54→63|`(8,6,10)`, 25점|무효→유효|
|B·M2·슬롯8 가용성 0→1|54→64|기존 `(1,6,10)`, 20점 유지|무효 유지|
|둘을 함께 대입|54→73|`(8,6,10)`, 25점|무효→유효|

원문상 잘못된 정보와 실제 제출이 연결되는 후보 사례이며, 오류를 대입한 문제의 유일 최적해가 실제 제출과 일치한다. 이것만으로 Agent의 내부 믿음이나 실패 원인을 인과적으로 확정하지 않는다. 특히 아래처럼 **B는 전달되지 않은 앞선 응답에서도 같은 무효 후보를 포함했다.**

## 6/25: 거절 문자열과 실제 후속 수정은 별개

|거절 위치|오류 문자열|후속 실제 행동|
|---|---|---|
|request-1 A, setup|`Symbols must contain 1-8 ASCII letters`|9글자인 `teamavail`을 `tavail`로 바꾸고 다른 사전 항목은 유지. 다음 정의와 B의 수락은 적용됨.|
|request-4 A, task|`Unknown predicate or invalid syntax: tpref(A,M1,0,4).`|모든 `tpref`를 합의된 `teampref`로 바꿨으나 다음 응답도 거절됨.|
|request-5 A, task|`Only one message kind`|`inform()` 뒤의 `request()`와 요약 질문 72개를 전부 제거. A 요약 72개만 m3으로 전달.|
|request-7 B, task|`Only one message kind`|`inform()` 뒤의 `propose()` 및 `(8,6,10)` 일정을 제거. 가용성 오류 두 개를 포함한 B 요약은 그대로 m4로 전달.|

A의 두 번째 거절은 첫 철자 교정이 없었다는 뜻이 아니다. 철자는 고쳤지만 두 종류가 남아 있었다. B의 거절된 제안은 peer가 받은 후보에 포함하지 않았다. 실제 전달 후보는 그 뒤 A의 m5가 최초다. 거절 메시지에서 내용 오류까지 검증됐다고 쓰거나, 문법 교정과 가용성 교정을 같게 취급하면 안 된다.

## 2/26·5/25: 최적 후보를 벗어났다가 명시 불가 사유로 복귀

두 회차 모두 **m2 `(1,6,10)` 최적 → m3 `(8,6,10)` 무효 → m4 `(1,6,10)` 최적**이다. m3·m4가 각각 `revise`로 전달됐으며, 두 revise 모두 양쪽 제출 전이라 실제 지워진 제출은 없었다. 마지막 양쪽 제출은 최적 일정이다.

- **2/26:** B는 m1에서 자기 팀 M1·슬롯8 가용성을 정확히 0으로 보냈지만 m3에서 무효 후보와 명시 `valid(...,1)`·`score(...,25)`를 전송했다. A는 m4에 `unavailable(M1,B1,8)` 사유, m1·m3 참조, 해당 가용성·유효성 질문 2개를 넣고 최적 후보로 복귀했다. B의 유효성 1은 확정 오류이며 A의 사유가 이를 명시 반박한다. B가 나중에 `valid(...,0)`으로 다시 적거나 질문에 peer 메시지로 답한 기록은 없다.
- **5/25:** B의 m2 개인 자료에 `AV B1 8 0`이 이미 있었지만 A는 m3에서 무효 후보와 `SCORE 8 6 10 25`를 보냈다. B가 m4에서 `WHY_UNAVAILABLE M1 B1 8`을 적어 최적 후보로 복귀했다. 이 m3에는 별도 유효성 1 주장이 없다.

두 점수 25는 개인 선호도의 단순 합계와 일치한다. 다만 무효 일정의 `score`가 무엇을 뜻하는지 불명확하므로 같은 고정 정책에 따라 **보류 2건**으로 유지했다. 2/26의 명시 유효성 오류를 5/25에 추가하지 않았으며, 6/25의 제안·수락만으로 별도 `valid=1` 주장을 만들어 채점하지 않았다. 무효 후보의 존재는 내용 주장과 별도로 관찰표에 남겼다.

## 최종 성공에 남아 있는 요약 오류와 제어 관찰

|위치|전달된 선호도|실제 값|후속 교정|
|---|---:|---:|---|
|2/26 m2 A·M3·슬롯7|2|4|없음. 별도 무효 후보 복귀와 구분.|
|3/26 m2 A·M1·슬롯5|3|5|없음.|
|5/26 m2 A·M3·슬롯6|3|5|없음. B의 일정 수락에 이 요약 교정은 없음.|

세 키의 회의·슬롯은 A 측 가용성이 0이다. 각 오류만 대입한 독립 검산에서 유효 일정 집합과 그 점수·최적·최종 제출은 변하지 않았다. 내용 오류 판정은 그대로 유지했다.

- **2/25:** 첫 JSON은 내용이 든 `summaries` 뒤에 같은 키의 빈 배열을 다시 넣어 `Duplicate JSON key: summaries`로 거절됐다. 다음 응답은 중복 빈 필드만 삭제해 기존 요약 72개를 전달했다. 자동 JSON 파싱의 마지막 값 우선 규칙으로 원문을 해석하지 않았다.
- **4/25:** A submit → B wait → A wait → B submit이다. 두 wait 사이 새 peer 메시지는 없고 A의 제출은 유지됐다.
- **6/26:** 마지막 m5는 최적 후보와 사전상 `aval=askvalid`, `ascore=askscore`인 질문 2개다. 이후 A·B submit으로 끝나 peer 답변은 없다. 질문을 유효성·점수 사실 주장으로 세지 않았다.

전체 task 제어 적용은 send25·revise4·submit20·wait2이며 setup 적용4개·거절5개를 합쳐 응답60개다. 미제출 stop이나 제어 제한으로 끝난 회차는 없다.

## 검산·직접 읽은 범위

- 고정 `observation-review-v3.1` 평가기로 10회 task29개·모든 필드와 제어응답60개를 자동대조했다. 단계별 실행 평가 소스는 같다. 전달된 모든 task의 source/wire/receiver 코덱·프레이밍 보존과 내용 판정을 별도로 확인했다. 전송 전 거절과 setup은 전달 task 분모에 넣지 않았다.
- 직접 독해한 task는 **17/29개**: 2/25 m1; 2/26 m1~4; 3/26 m2; 5/25 m1~4; 5/26 m2~3; 6/25 m3~6; 6/26 m5. 거절5개 전체, 2/26·5/25 revise/submit, 4/25 submit/wait, 5/26 submit, 6단계 두 회차의 사전·최종 submit도 읽었다. 6/25는 원본 action payload를 읽고 packet sender_source와 완전 동일함을 확인했다. 나머지는 자동대조·정규화 검토이며 완전 수동 전수검수는 아니다.
- 추출 주장 **1,447개(요약1,224·개인사실216·점수3·유효성2·사유2)**, 전체 후보17개·최종10개를 기존 평가기의 산술 함수를 사용하지 않고 재계산했다. 보류 점수의 합계25도 별도 확인했으며 모든 기존 판정과 일치했다. 주장 추출은 기존 파서에 의존한다. 1,728개 배정 중 유효54개·유일 최적20점도 독립 확인했다.
- 오류5개의 요약 대입 효과, 오류의 후속 교정 여부, 거절 뒤 실제 수정·제거, revise 당시 제출 상태, wait와 마지막 질문 이후 무전송을 별도로 확인했다. 선택한 원본 회차 파일과 실행 소스 해시는 전후 동일하다. 원본·소스·설정 변경 및 추가 모델 호출은 없다. 방식의 우열·비용 순위 일반화는 하지 않았다.
