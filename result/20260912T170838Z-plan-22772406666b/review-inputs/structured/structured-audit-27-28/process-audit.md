# 2~6단계 trial27~28 추가 감사

10회 모두 유효한 일정을 양쪽이 제출해 성공했다. **3/27만 19점(최적 대비 1점 차이), 나머지 9회는 20점**이다. 내용 주장 발생 수는 **정답 1,414 / 오류 12 / 보류 1**이며 task42개·코덱 오류0개다. 별도 거절10건은 3/27 네 건, 3/28 두 건, 6/28 네 건이다.

## 3/27: 다른 참석자 집합의 값과 일치하는 M1 요약, 미교정·19점

A의 m1은 B·M1·슬롯0의 가용성 한 개를 질문했다. B m2는 가용성1과 함께 질문하지 않은 선호도4도 보냈는데 실제 선호도는2다. A m3는 자기 요약72개와 나머지71개 키의 질문을 보냈고, B m4는 전체 요약72개를 답했다. m4에는 **M1의 오류11개**가 있으며, 슬롯0 선호도 오류는 m2의 값이 반복된 것이다. 그래서 오류는 발생 수12·고유 키11개다. 뒤의 A m5 `(7,6,10)` 제안과 양쪽 제출까지 명시 교정은 없다.

원자료와의 독립 대조에서 **m4의 B·M1 가용성·선호도 24개가 B1+B2 계산값 및 같은 메시지 B·M2의 24개 값과 모두 일치**한다. 실제 M1의 B 참석자는 B1 한 명이다. 부모의 별도 요청으로 읽은 **3/07 m2의 B·M1 24개도 전부 같은 값**이다. B 인원 7개 부분집합 중 24/24개가 일치한 집합은 B1+B2뿐이다. [24개 값 비교표](pattern-comparison-3-07-27.md)에 원문·원자료를 나란히 남겼으며 내부 생성 원인을 추정하지 않았다. 3/07은 이번10회 지표에 합치지 않았다.

특히 `teamavailable(B,M1,1,0).`는 실제1과 달라 원래 최적 `(1,6,10)`을 제외한다. 이 오류 하나만 대입하면 최적 점수는20→19가 된다. 실제 제출 슬롯7의 `teampreference(B,M1,7,3).`도 실제1보다 크다. **11개 오류를 함께 대입**한 독립 검산에서는 유효 일정이54→26개이고 유일 최적은 실제 제출 `(7,6,10)`, 대입 문제의 점수21이다. 원래 문제에서 같은 제출은19점이다. 이 일치는 후속 선택과 잘못된 정보의 관계를 보여 주지만 Agent의 내부 믿음이나 인과를 확정하지 않는다. 원문에는21점이라는 별도 주장이 없다.

첫 전송 전 A가 네 번 거절됐다. request-1·2는 같은 `asksumary` 응답을 반복했고, request-3은 `asksumary(availability,...)` 질문72개, request-4는 `asksumm ary(available,B,M1,0).` 질문1개였다. 다음 m1에서 이름의 공백을 고쳐 전달했다. 최초 실패에 담겼던 A 요약72개는 나중 m3에서 그대로 전달됐다. 문법 교정과 B의 내용 오류 미교정은 별개다.

## 3/28·6/28: 거절 이후 실제 수정과 정보 요청

- **3/28:** B의 처음 응답은 `asksummary(availability,...)`로 `Invalid question type or arguments` 거절을 받았다. 다음에는 자기 요약을 빼고 개인 `askfact(available/preference,A1~A3,...)` 질문72개를 보냈다. A의 응답은 개인 사실이 아니라 **팀 요약72개**다. 질문과 답의 종류가 달라 동일한72개 필드에 직접 답했다고 표현하지 않았다. A가 자기 정보와 질문을 두 종류로 묶은 응답은 `Only one message kind`로 거절됐고, 요약만 먼저 보낸 뒤 같은 B 요약 질문72개를 m4에서 그대로 다시 전달했다. B의 답과 최적 후보 수락을 거쳐 종료됐다.
- **6/28 사전:** B 정의 뒤 A가 같은 사전을 `accept_language`에 넣어 `Only define_language can contain a dictionary`로 거절됐다. A는 **사전 값을 바꾸지 않고** action을 `define_language`로 바꾸어 다시 정의했고 B가 수락했다. 적용된 setup 메시지는3개다. 새 기호를 협상해 바꾼 사례로 표현할 수 없다.
- **6/28 task:** A는 `inf()`·`pro()` 중복을 고친 뒤에도 합의되지 않은 원래 이름 `askvalid` 때문에 다시 거절됐다. `aval`·`ascore`로 바꾸어 후보·요약6개·질문2개를 전달했다. B는 `inf()`·`req()` 중복으로 거절된 뒤 `req()` 줄만 제거하여 점수·유효성 답과 요약 질문72개를 모두 유지했다. 질문은 답변받았고 후보는 계속 `(1,6,10)`이었다.

5/28과6/28의 A 요약은 후보에 붙인6개 뒤 전체72개를 보내 각각78회 발생·72고유·6반복이다. 후보 변경이나 내용 교정으로 세지 않았다. 5/28의 이 대조는 자동 필드 비교이며 해당 원문 전체는 직접 독해 범위 밖이다.

## 검산 범위

- 고정 `observation-review-v3.1`로10회 task42개·제어77개 전체 필드를 자동대조했다. 적용 task는 send37·revise5·submit20, setup5개와 거절10개가 별도다. 질문510개를 사실 주장으로 세지 않았다. 전달 task의 source/wire/receiver·프레이밍 보존과 내용 정답 판정은 분리했다.
- 직접 읽은 task는 **28/42개**: 2/28 m1~6; 3/27 m1~5; 3/28 m1·2·4; 4/27 m2·3; 4/28 m2~4; 6/27 m3~6; 6/28 m4~8. 거절10개 전체, 이 회차들의 revise·최종제출, 6단계 사전도 읽었다. 원본 action payload로 읽은 내용은 packet sender_source와 같음을 확인했다. 별도3/07 m2를 값 비교에만 읽었다. 완전 수동 전수검수는 아니다.
- 추출 주장 **1,427개(요약1,126·개인사실288·점수5·유효성5·사유3)**, 전체 후보20개·최종10개를 기존 평가기의 산술 함수 없이 재계산해 판정 일치를 확인했다. 무효 score23은 산술 합계만 검산했고 보류를 유지했다. 주장 추출은 기존 파서에 의존하며 3/07·27 비교는 원문의 별도 정규식 추출과 인원 부분집합 산술도 사용했다. 원래 문제의1,728개 배정·유효54개·유일 최적20점을 확인했다.
- 선택한10회 및 추가3/07 원본 파일과 단계별 실행 소스의 해시는 전후 동일하다. 원본·소스·설정 변경, 추가 모델 호출은 없다. 방식의 우열·비용 순위로 일반화하지 않았다.
