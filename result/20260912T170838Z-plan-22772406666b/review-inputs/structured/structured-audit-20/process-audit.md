# 2~6단계 trial20 감사

5회 모두 최종 `(M1,M2,M3)=(1,6,10)`, 유효·20점이다. 내용 주장은 **정답 730 / 오류 0 / 보류 0**, task 메시지는 22개, 전달된 메시지의 코덱 오류는 0건이다. 최초 후보는 2단계에서 불가능했고 6단계에서 유효·16점이었으며, 두 후보 모두 최종 수정됐다. 문법·프로토콜 거절은 별도로 6건이다.

## 6단계20: 사전 합의, 사용 오류, 정보 교환, 후보 수정

기록의 메시지 **11개는 setup 2개 + task 9개**다. 제어 응답은 18개(적용 13개·거절 5개)다. 사전 합의 자체에는 거절이 없었다.

|구간|원문·실제 진행|
|---|---|
|사전 합의 request-1~2 / m1~2|B가 정의하고 A가 수락. 예: `request→req`, `ask→ask`, `asksummary→asksum`, `available→avail`. 정의·수락 모두 첫 시도에 적용됨.|
|초기 정보 m3|B가 자기 팀 전체 요약 72개를 전달.|
|A의 거절 request-4|A가 `info()`와 `prop()`를 함께 넣어 `Only one message kind`로 거절됨. 전체 A 요약 72개와 `(1,2,10)` 후보를 담았지만 peer에게 전달되지 않음.|
|첫 후보 m4 / request-5|A는 정보 부분을 빼고 `(1,2,10)` 제안만 전달. 이 일정은 독립 검산상 **유효·16점**이다. A가 점수 16이나 최적성을 명시한 것은 아니다.|
|B의 거절 request-6~9|네 응답 모두 `ask().`로 시작하며 `Invalid predicate arguments`로 거절됨. 본문은 유효성·점수 질문 → 후보 슬롯 요약 질문 → 개인 가용성 질문 → 같은 개인 질문의 타입 인수 변경 순서. 이 네 질문은 모두 전달되지 않음.|
|개인 사실 요청 m5~6|B가 `req().`와 `askfact(available,A1,1).`를 전달하고 A가 `avail(A1,1,1).`로 응답. **1개 요청·1개 응답**.|
|후보 슬롯 요약 m7~8|B가 `(1,2,10)`의 A 팀 가용성·선호도 **6개**를 요청하고 A가 정확히 해당 6개에 응답.|
|전체 요약 m9~10|B가 A 팀 전체 요약 **72개**를 요청하고 A가 모두 응답. m8의 6개는 같은 값으로 반복됨. m10은 A의 앞선 거절 request-4에 있던 정보 부분과 완전히 동일함.|
|후보 변경 m11 / request-16|B가 `revise`로 `(1,6,10)`을 제안. 독립 검산상 **유효·20점**이다. 이 메시지에도 명시 점수·유효성·최적성 주장은 없고 후보만 있다.|
|제출 request-17~18|A, B 순서로 새 후보를 제출해 성공. revise 전 제출은 없어서 `cleared_agents=[]`. 이 회차에는 **wait와 stop이 없다**.|

사전에서 `ask`는 `ask(A1).`처럼 개인 정보를 요청하는 술어이고 메시지 종류 `request`의 기호는 `req`다. 따라서 인수 없는 `ask().`가 네 응답의 첫 오류다. request-9에는 `askfact(avail,A1,1)`도 있지만 실제 오류는 앞의 `ask().`에서 발생하므로 이를 별도 거절로 중복 계산하지 않았다. 적용된 m5에서는 종류를 `req()`로, 질문의 타입 인수를 `available`로 바로잡았다.

이 회차가 길어진 기록은 **종류 중복 거절 1회, 잘못된 `ask()` 사용 거절 4회, 요청 범위 1→6→72개 확대, 후보 16→20점 변경**으로 나눌 수 있다. m8→m10의 같은 키 6개 반복을 확인했지만, 자료를 받은 것이 내부 판단을 어떻게 바꿨는지 또는 재요청이 필수였는지는 단정하지 않는다. 사전 합의 지연·wait 반복·제출 무효화가 길이 증가 원인이었다고 쓰면 원문과 다르다.

## 나머지 단계에서 확인한 점

- **2단계:** m2 A는 `(3,6,10)`을 제안하면서 유효성과 점수를 질문했다. B1이 M1 슬롯 3에 불가하다. m3 B는 정확한 `unavailable/M1/B1/3` 사유와 `(1,6,10)` 대안을 제안하고 새 후보의 평가를 질문했다. m4 A는 새 후보를 수락하며 유효·20점을 명시했다. 이전 후보의 질문을 잘못된 사실 주장이나 점수 보류로 세지 않는다. 이전 후보에 대한 별도 점수 응답은 없다. 후보 변경은 합의·제출 전에 `send`로 이뤄졌고 실제 revise는 없다.
- **3단계:** 첫 질문의 `availability`를 `available`로 바꾼 뒤 적용됐다. 양쪽 팀 요약 72개씩 요청·응답하고 A가 최적 후보를 제안했다. B의 마지막 `accept().`에는 일정 값이 없으므로 여기에 새 전체 후보나 유효성 주장을 추가하지 않았다. 양쪽 최종 제출은 같은 최적 일정이다.
- **4단계:** B 요약과 A 요약 요청, A의 요약 응답·최적 후보, 양쪽 제출로 완료됐다. 해당 두 task는 자동대조 범위다. 4단계는 고정 의미 특성 벡터 구현이다.
- **5단계:** B 제출 → A wait → B wait → A 제출로 완료됐다. 두 wait 동안 B 제출이 유지됐고 **후보 전달 이후 새 peer 메시지는 없었다**. 수락 메시지 수신 후 제출했다고 표현하면 안 된다. wait의 의도는 판단하지 않는다.

전체 적용된 task 제어는 `send 21 / revise 1 / submit 10 / wait 2`다. setup 적용 2개와 task 거절 6개를 합쳐 총 제어 응답 42개다. 모든 회차는 양쪽 제출로 종료됐다.

## 독립 검산과 읽기 범위

- 같은 고정 `write_trial_records`와 `observation-review-v3.1`로 5회 전체를 임시 출력에 재계산하고 task 22개·제어 응답 42개를 대조했다. 질문 371개는 사실 주장으로 세지 않았다. 전달된 내용·코덱 평가와 전달 전 거절을 분리했다.
- 직접 읽은 task 원문은 **20/22개**: 2단계 m1~4, 3단계 m1~5, 5단계 m1~2, 6단계 m3~11. 거절 응답 6개 전체, 6단계 사전·정의/수락·revise/제출 응답, 5단계 제출/wait 응답도 읽었다. 4단계 두 task는 자동대조·정규화 결과 검토이며 완전 수동 전수검수로 표현하지 않는다.
- 기존 평가기 산술 함수를 쓰지 않고 추출 주장 **730개(요약 726, 개인 사실·사유·일정 점수·유효성 각 1)**, 전체 후보 8개·최종 5개를 원본 문제에서 재계산했다. 모두 기존 판정과 일치했다. 질문키와 응답키, A의 거절된 전체 요약과 이후 전달된 요약의 동일성, 같은 키 6개 반복, wait 중 제출 유지도 검산했다. 추출 자체는 기존 파서를 사용했다.
- 1,728개 일정 중 유효 54개, 유일 최적 20점을 확인했다. 선택 원본 파일 및 실행 소스 해시는 전후 동일하고 단계별 평가 소스도 같다. 코어·설정·원본 수정과 추가 모델 실행은 없었다. 방식의 우열이나 비용 순위의 일반화는 이 감사에 포함하지 않는다.
